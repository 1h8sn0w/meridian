# tools — скрипти репозиторію

## `v1-export.js` — забрати дані з Meridian V1 (MER-48)

`localStorage` прив'язаний до origin, тож дотягнутися до даних V1 ззовні — ні
скриптом на сервері, ні з іншої вкладки — неможливо. Єдиний спосіб — виконати
код **на сторінці V1**.

1. Відкрити Meridian V1 **на тій самій адресі, де ним користуються.**
   Це найважливіший крок: `file://` — це інший origin і інше (порожнє) сховище,
   тож відкритий «з файлу» застосунок покаже нуль записів, хоча дані на місці.
2. Відкрити консоль браузера (F12 → Console).
3. Вставити вміст `v1-export.js` цілком і натиснути Enter.
4. Браузер збереже `meridian-v1-export.json`.
5. У V2: вкладка **«Сім'я» → «Перенести дані з V1»** → вибрати файл.

V2 спершу показує, що саме приїде і що НЕ приїде та чому, і лише після
підтвердження записує. Повторний імпорт того самого файлу нічого не подвоює —
id рядків виводяться з id V1 (`derivedId` у `@meridian/core`).

### Що переноситься

| Дані V1 | Куди у V2 |
|---------|-----------|
| `meridian.meals.v1` | `meal` + `recipe` (кроки, час, порції, фото — окремим рядком) |
| `meridian.mealPrefs.v1` | `meal_pref` (MER-18) |
| `meridian.profiles.v1` | `profile`, разом зі спільним планом і підмножиною страв |

### Що НЕ переноситься — і чому

| Дані V1 | Чому |
|---------|------|
| `meridian.week.v1.*` | V1 клав у план **знімки** страв, а `plan_slot` у V2 посилається на страву з пулу. Знімок страви, яку потім видалили, подіти нікуди. Тиждень генерується наново |
| `meridian.calendar.v1.*` | Історія лишається у V1; календар V2 починається з дня імпорту |
| `meridian.shopping.v1` | Позначки прив'язані до відбитка планів, яких не буде |
| `meridian.app.v1` | Стан інтерфейсу: у V2 активний екран — це адреса маршруту |

Альтернативи для історії розглянуто й відхилено: переносити лише «живі» дні
означало б дірки саме там, де страву колись прибрали, а створювати страви зі
знімків — засмітити пул тим, чого в ньому не було (генератор почав би це
пропонувати). Прожиті тижні лишаються у V1, який нікуди не дівається.

Кожен пропущений запис — і ключ сховища, і окрема страва чи профіль — приїжджає
в список `skipped` із причиною й показується на екрані. Тихо підставлене типове
значення виглядало б як успішна міграція.

## `check-comments.mjs` — храповик «нуль коментарів» (MER-92)

Код читають і пишуть агенти, тож коментарів у ньому не має бути: нюанс модуля
живе в `README.md` його теки, інваріант — у тесті з назвою-реченням, намір — в
імені. Храповик не пускає коментарі назад у теки, які вже почищено.

Дві перевірки, один список тек — `COMMENT_FREE_DIRS` у `check-comments.mjs`:

| Що | Чим | Коли |
|----|-----|------|
| JS/TS/TSX (і JSX-коментарі) | правило `meridian/no-comments` у `eslint.config.base.mjs` | `pnpm lint` у пакеті |
| SQL, YAML, Caddyfile, Dockerfile, sh, CSS, HTML | сам `check-comments.mjs` по `git ls-files` (з новими, ще не доданими файлами) | `pnpm lint` у корені, перед ESLint |

Обидві беруть шлях від кореня репозиторію й перевіряють, чи він у теці зі
списку. Поза списком не перевіряється нічого.

### Як додати теку

1. Почистити теку: кожен коментар або вже сказаний у README чи AGENTS (тоді
   видалити), або стає тестом, іменем чи розділом README теки під заголовком з
   ім'ям експорту (`### saveWeek`).
2. Дописати шлях теки від кореня без скісної риски в кінці в
   `COMMENT_FREE_DIRS` (`'packages/core/src'`). Тека береться разом із
   підтеками.
3. `pnpm lint` має бути зеленим.

Список росте лише вгору: тека, що вже в ньому, звідти не виходить.

### Що дозволено

- Директиви інструментів у JS/TS: `eslint-disable`/`eslint-enable` (з описом
  після `--`), `/* eslint … */`, `/* global … */`, `@ts-check`, `@ts-nocheck`,
  `@ts-expect-error`, `@ts-ignore`, `/// <reference …>`, `#__PURE__`,
  `@vite-ignore`, `prettier-ignore`. Невикористаний `eslint-disable` — помилка
  (`reportUnusedDisableDirectives: 'error'`), тож директиви не протухають.
- Шебанг (лише в першому рядку), `# yaml-language-server:`, `# syntax=`.
- `#`, `--`, `/*` усередині рядка в лапках коментарем не є.

### Винятки за шляхом

`EXCEPTIONS` у `check-comments.mjs` — не перевіряються навіть у чистій теці:
застосовані міграції `0000–0007` (історія, не переписуємо; нові міграції без
коментарів, пояснення — рядком у таблиці «Міграції» в `packages/db/README.md`),
нативні `apps/web/android/` та `ios/`, згенерований `routeTree.gen.ts`, шаблони
issue і PR у `.github/` та `.env.example` (їх читає людина, що хостить сама).

### Відомі стелі (ponytail)

- Коментар шукається регулярним виразом по рядку, не парсером. Рядки в лапках
  вирізаються, але лапки через кілька рядків чи екрановані лапки сканер не
  розбирає. Якщо почне хибити — парсер формату замість виразу.
- ESLint ходить лише в пакети (`apps/web`, `packages/core`). JS у корені й у
  `tools/` (як цей скрипт) не лінтиться, тож храповик для них не спрацює —
  коли до них дійде черга, додати кореню свій `eslint.config.js`.
