# @meridian/core — доменна логіка

Домен чистим TypeScript (MER-47, порт V1), без фреймворків і БД: той самий
код іде у веб, Capacitor і натив. `index.ts` експортує лише те, що імпортує
споживач: кожне ім'я в барелі — обіцянка; модулі й тести імпортують одне
одного напряму.

## Модулі

| Модуль | Що робить |
|--------|-----------|
| `types.ts` | Доменна модель: `null` замість NULL, розібраний JSON замість `jsonb` |
| `provenance.ts` | Провенанс, розбір чисел, денна сума |
| `plans.ts` | Належність страви до планів дієтолога, структурно (MER-30) |
| `generator.ts` | Тиждень і достатність пулу (`poolShortage`, `poolShortageMessage`) |
| `replace.ts` | Ручна заміна слота (MER-12, MER-28) |
| `calendar.ts` | Дати, антиповтор через межу тижнів (MER-29) |
| `profile.ts` | Пул профілю, власник спільного плану (MER-17) |
| `rows.ts` | Рядок локального SQLite → доменний об'єкт |
| `sync-ids.ts` | Id, виведені з природного ключа (MER-57) |
| `shopping.ts` | Список покупок і відбиток плану (MER-62) |
| `migrate-v1.ts` | Дамп `localStorage` V1 → рядки V2 (MER-48) |
| `parse-plan.ts` | Текст плану дієтолога → кандидати (MER-52) |
| `starter-set.ts` | Формат і перевірка стартового набору (MER-77) |
| `check-starter-set.ts` | `pnpm starter:check`; єдиний модуль із Node |

## Рішення ядра

- **Жодних сховищ.** Пул, профіль, смаки й минулі дні — аргументи. Форму рядка
  знає лише `rows.ts`.
- **Випадковість — параметр** (`random`), інакше тиждень не перевірити
  тестом; у тестах — `seeded` (mulberry32) на кількох зернах.
- **Помилка — значення:** `{ ok: true, … }` або `{ ok: false, error }`
  українською. Винятки — лише на зіпсованих даних: рядок (`rows.ts`), число,
  дата, файл не-дамп (`migrateV1`).
- **`calories` nullable.** Генератор і заміна страву без калорій не беруть
  (нуль був би вигадкою) і кажуть про це. У `DayCalories` (похідне, MER-44)
  `unknown` — слоти без цифри, `approx` — є оцінка; неповна сума «≈» не має.
- **Провенанс — кодом, а не колонкою.** `hasValue`: `null`/`undefined`,
  NaN/±∞, порожній після trim рядок і порожній масив — «немає»; нуль і `false`
  — значення. Секція БЖВ видна, якщо є хоч одне з трьох; пропуск у
  ній — «—». Калорій немає — порожньо, «≈» лише з `caloriesApprox` (MER-26).
  `?? 0` у ядрі не буває.
- **`Meal.source` — підпис плану дієтолога, а не provenance-енум**
  (`'pdf' | 'manual'`): на ньому стоїть мікс. `""` — плану не вказано.
  `gerd` генератор поки не враховує.

## Генератор тижня

### generateWeek

На кожен слот дня — одна страва, так щоб: (1) тип збігався; (2) день був у
коридорі від цілі (`DEFAULTS`: 2000 ±100 ккал); (3) страва не повторювалась у
вікні `antiRepeatDays` (типово 3; понад довжину тижня — «без повторів»),
зокрема через межу тижнів; (4) тиждень міксував плани. Ціль і коридор — із
`options.profile`, явні опції головніші; підмножина `mealIds` звужує пул.

Пошук (MER-27): день — перебір по слотах, вужчі першими, з відсіканням за
межами залишку суми; тиждень — DFS між днями,
до `DAY_VARIANTS_PER_NODE` варіантів дня на вузол, стеля
`DAY_PLACEMENTS_PER_TRY` проти зависання, `WEEK_TRIES_PER_CORRIDOR` спроб на
рівень. Не склалось — коридор ширшає на `CORRIDOR_STEP` до `CORRIDOR_MAX`
(±500); сам `CORRIDOR_MAX` пробується окремо, бо крок може його перестрибнути
(MER-38). Кожне послаблення — у `warnings`, single-source-тиждень — окремим
попередженням, а не тихим успіхом.

`precedingDays` (будує `precedingMealIds`) заповнює вікно антиповтору перед
днем 0: індекс 0 — учора.

### Смаки (MER-18)

Смак — окремий рядок `meal_pref`, а не поле страви: він не з плану дієтолога.
Правила дієтолога смаком не послаблюються. Улюблені — вага `FAVORITE_WEIGHT`
у зваженому перетасуванні (Ефраїмідіс–Спіракіс, `U^(1/вага)`), а не гарантоване
місце, інакше тижні однакові. Небажані виключаються першою спробою; без них не
збирається — повний пул і пояснення.

### suggestReplacements / replaceSlot

Кандидат позначається `valid` + `reasons` (коридор, повтор поруч в обидва боки
вікна, мікс); UI блокує невалідних (MER-28). Порядок: валідні, не-небажані,
улюблені, у коридорі, без повтору, ближчі до цілі. Смак міняє лише порядок і
позначку. `replaceSlot` повертає новий план і перевіряє лише цілісність (день,
слот, тип) — свідомий вибір за користувачем.

### mealPlans / isMixedWeek (MER-30)

Мікс за кількістю підписів давав хибнопозитив: десерт «Тиждень 1–2» рахувався
третім планом. Тому належність — множина планів: діапазон у підписі
розгортається (до `MAX_PLAN_RANGE`), страва без джерела — wildcard. Тиждень
зміксований ⇔ жоден один план не покриває всі його страви; мікс можливий
(`mixPossibleIn`), коли планів ≥ 2 і жоден не покриває весь пул.

## Календар і профіль

**Дата — рядок `YYYY-MM-DD`,** як колонка `date`. `addDays` рахує через
`Date.UTC`: у ніч переведення годинників локальна доба ≠ 24 год (MER-31).
Дат-об'єктів ядро не повертає. Тиждень — з понеділка.

**`precedingWindow`** = `antiRepeatDays - 1` окремою функцією: у V1 «-1» на
місці виклику загубили. День без записів — `[]`, бо позиція означає «як
давно».

**`poolForProfile`:** `mealIds = null` — увесь пул, `[]` — жодної страви.
**`planOwnerId`** робить один крок: ланцюжки спільних планів забороняє CHECK.

## rows.ts

SQLite має TEXT, INTEGER, REAL: boolean приходить `1`/`0` (з Postgres —
`true`/`false`), `jsonb` — текстом (або вже масивом). Розбір суворий:
зіпсоване — помилка, не значення за замовчуванням. Рядок без колонки `gerd`
(схема ще не доїхала) — `false`, як DEFAULT у міграції. Порожні кроки
рецепта — артефакт `textarea`, відкидаються. М'яко видалені рядки відсіює
запит викликача.

## Виведені id (sync-ids.ts)

LWW розсуджує зміни рядка, але не дві незалежні вставки: під частковим
унікальним індексом друга падає (`23505`), конектор вважає клас 23 фатальним, і
дія користувача тихо зникає. Тому обидва пристрої рахують один UUIDv5 із
колонок індексу, і вивантаження стає upsert. Виведений id — лише для
вставки: наявний рядок шукається за природним ключем (див.
`apps/web/src/lib/data`, `lib/powersync`).

- **`MERIDIAN_NAMESPACE` не змінюється ніколи** — «золоті» значення в
  `sync-ids.test.ts` валять тест, а не дані. `uuid` — єдина рантайм-залежність,
  свідомо.
- **`derive`** склеює складники через NUL (`SEP`, записаний екрановано: живий
  NUL робить файл двійковим для ripgrep). Перший складник — таблиця чи сім'я,
  тож різновиди не перетинаються. Експортується для `shopping.ts`, у барель —
  ні.

| Функція | Ключ | Чому так |
|---------|------|----------|
| `derivedId` | сім'я, різновид, id V1 | Повторний імпорт оновлює ті самі рядки; профіль V1 `default` однаковий у всіх |
| `mealPrefId` | `meal_id` | Сім'ю вже визначає страва |
| `shoppingCheckId` | сім'я, `item_key`, відбиток | `item_key` — вільний рядок, у сім'ях збігається |
| `planSlotId` | профіль, дата, слот | Без `week_plan_id`: перегенерація переписує ту саму клітинку (MER-49) |
| `recipeId` | `meal_id` | Індекс не частковий: будь-який наявний рядок, навіть видалений, оновлюють |
| `familySettingsId` | сім'я | Один рядок на сім'ю |
| `starterMealId` | сім'я, `key` набору | Повторний засів оживляє видалений рядок, а не дублює |

## Список покупок (shopping.ts)

Список не зберігається — щоразу з інгредієнтів слотів (страва двічі — дві
потреби). `aggregate` сумує лише однакові назву й одиницю; без кількості —
окремий перелік назв, «типових» грамовок немає. Категорія — за точною назвою з
`CATEGORY_BY_NAME` (назви демо-пулу), невідома — «Інше»; `Map`, бо в об'єкта є
`constructor`. `nameKey` лягає в `item_key` позначки — після першого запису не
міняти.

### planFingerprint

Відбиток — «той самий похід у магазин»: позначки фільтруються за ним, а не
стираються (MER-55). Рахується зі змісту — відсортованих пар
«клітинка~страва» (у uuid `~` не буває), — а не з `week_plan`: той має
випадковий id і різниться між пристроями, а `generated_at` — текст різної
форми.
Ціна: ручна заміна страви скидає позначки (у V1 — ні); список тоді справді
інший. Охоплення не входить, клітинки беруться всіх профілів. Порожній рядок —
плану немає. Поки йде перша синхронізація, відбиток міняється з чекпоінтами:
позначка тих секунд помітно знімається, повторний дотик її повертає.

## migrateV1

Чиста функція; що й чому не переноситься — `tools/README.md`. Кидає лише на
файлі, що не є дампом; решта — `skipped` із причиною, бо тиха підстановка
виглядала б як успіх. Некоректне поле відкидає весь запис; виняток — колір
профілю (`FALLBACK_COLOR`), він інтерфейсний. Зіпсований рецепт не забирає
страву. Рецепт — лише якщо є хоч одне з чотирьох полів. Id смаку — зі страви
(`mealPrefId`), не з ключа V1. `sharedPlanWith` зводиться другим проходом;
власник не переїхав — профіль отримує власний план.

## parsePlanText (MER-52)

PDF читає веб (`lib/pdf-text.ts`). Береться лише буквальне: калорії —
з «N ккал», зокрема в заголовку слота (MER-41); БЖВ — ніколи («Ж» і «Ч» — порції
Жінка/Чоловік, MER-24); інгредієнт структурується лише з «число + г/кг/мл/л»;
«Готова порція» — дослівно, прив'язана до складника (рядок без крапки перед
нею); речення з крапкою — кроки; «На 2-х» — `servings: 2`, «-» — без нових
продуктів; назва десерту відрізається механічно й позначається на перевірку.
Перенесені рядки склеюються (мала літера, цифра, дужка, розділовий знак,
«Ж -»/«Ч -»). `kind`: `meal`; `repeat` («Той самий…», у пул не йде); `dup` (назва
вже була, типово не імпортується). Результат — кандидати поруч із сирим текстом.

## Стартовий набір: формат файлу (MER-77)

Страви з планів дієтолога для засіву пулу нової сім'ї. Файл — на сервері
**поза репозиторієм**; підключення — в
[`infra/README.md`](../../infra/README.md#стартовий-набір-страв), вигаданий
приклад — [`infra/starter-set.example.json`](../../infra/starter-set.example.json).
`pnpm starter:check <файл>` — та сама `parseStarterSet`, що перед засівом.
Будь-яка помилка — не засівається нічого; показуються до `MAX_ERRORS` помилок
одразу.

Верхній рівень: `{ "version": 1, "meals": [ … ] }`. Усі поля страви
обов'язкові, **навіть порожні** (`null`, `[]`, `""`); невідоме поле — помилка.
Межі — як у схемі БД.

| Поле | Тип | Що це |
|------|-----|-------|
| `key` | непорожній, унікальний | Стабільний ключ → id рядка (`starterMealId`). Не змінювати: новий ключ — нова страва |
| `name` | непорожній | Назва |
| `type` | `breakfast`/`lunch`/`dinner`/`snack` | Слот |
| `calories` | ціле `>= 0` / `null` | `null` — немає в джерелі, генератор не бере |
| `caloriesApprox` | boolean | «≈» (MER-26); `true` без `calories` — помилка |
| `protein`, `fat`, `carbs` | число `>= 0` / `null` | Грами |
| `ingredients` | масив | Рядок або `{ "name", "amount"?, "unit"? }` |
| `portions` | `{ "component", "text" }[]` | Рядок після «Готова порція:» дослівно (MER-24) |
| `source` | рядок | Підпис плану для міксу; `""` — не вказано |
| `gerd` | boolean | Маркер «ГЕРХ» (MER-75) |
| `sourceIssues` | непорожні рядки | Розбіжності джерела дослівно, без «правильного» значення (MER-76) |
| `recipe` | об'єкт / `null` | `steps` (непорожні рядки), `prepTime` (ціле `>= 0` / `null`, хв), `servings` (ціле `>= 1` / `null`) |

Фото в наборі немає — лише від користувача.

### Як засівається

- **Автоматично — раз на сім'ю й лише в порожній пул**
  (`family.starter_seeded_at`). Стара сім'я з непорожнім пулом лише
  позначається.
- **Позначка — після запису страв;** формат і порожнечу перевіряють до нього,
  тож зіпсований файл засів не «спалює».
- **Решта — кнопкою «Додати стартовий набір»** на «Стравах»: видна, коли в
  наборі є відсутні в пулі страви, і додає лише їх. Так повертаються страви
  очищеного пулу й нові з оновленого файлу.
- **Наявних страв засів не переписує:** той самий `key` лишається як є.
  Порожній рецепт (`hasRecipe`) рядка не створює.

## Тести

`node --test`; Node стирає типи сам, тому `erasableSyntaxOnly` (без
`enum`/`namespace`) і імпорти з `.ts`. Збірки `dist` немає (MER-104):
`package.json` експортує `src/index.ts`. `typecheck` проганяє ще
`tsconfig.domain.json` без типів Node, тестів, `test-support.ts` і
`check-starter-set.ts` — глобаль Node у домені падає. Тести генератора
покривають межові випадки V1 (MER-18, 26, 27, 29, 30, 38). `weekViolations`
перевіряє правила 1–3; мікс — окремі тести: його генератор може свідомо
послабити.
