# @meridian/core — доменна логіка

Домен чистим TypeScript (MER-47), без фреймворків і БД: той самий код — у
вебі й у тестах. `index.ts` експортує лише те, що імпортує споживач; модулі
й тести імпортують одне одного напряму.

## Модулі

- `types.ts` — доменна модель: `null` замість NULL, розібраний JSON замість
  `jsonb`.
- `provenance.ts` — провенанс, розбір чисел, денні суми калорій і БЖВ.
- `plans.ts` — належність страви до планів дієтолога; `generator.ts` —
  тиждень і достатність пулу (`poolShortageFor`); `replace.ts` — ручна заміна
  слота (MER-12).
- `calendar.ts` — дати, антиповтор через межу тижнів (MER-29); `profile.ts` —
  пул, порція й слоти профілю, власник спільного плану.
- `rows.ts`, `sync-ids.ts` (MER-57), `shopping.ts` (MER-62), `migrate-v1.ts`
  (MER-48), `parse-plan.ts` (MER-52), `starter-set.ts` (MER-77) — розділи
  нижче; `check-starter-set.ts` — `pnpm starter:check`, єдиний модуль із Node.

## Рішення ядра

- **Жодних сховищ.** Пул, профіль, смаки й минулі дні — аргументи.
- **Випадковість — параметр** (`random`), щоб тиждень перевірявся тестом
  (`seeded` на кількох зернах).
- **Помилка — значення** (`{ ok: false, error }`). У генератора й заміни —
  коди з параметрами, текст — словник застосунку (MER-128); деінде `error` —
  рядок українською. Кидає ядро лише на
  зіпсованих даних: рядок (`rows.ts`), число, дата, файл не-дамп
  (`migrateV1`).
- **`calories` nullable.** Страву без калорій генератор і заміна не беруть
  (нуль був би вигадкою) і кажуть про це. `DayCalories` (MER-44): `unknown` —
  слоти без цифри, `approx` — є оцінка; неповна сума «≈» не має. `dayMacros` —
  те саме для кожного з БЖВ; `known` відрізняє нуль від «жодної цифри»
  (MER-144).
- **Провенанс — кодом, а не колонкою.** `hasValue`: `null`/`undefined`,
  NaN/±∞, порожні рядок і масив — «немає»; нуль і `false` — значення. БЖВ
  видно, якщо є хоч одне з трьох, пропуск — «—». «≈» — лише `caloriesApprox`
  (MER-26) чи `macrosApprox` (MER-141); `unit` — зі словника. `?? 0` у ядрі
  не буває.
- **Цифри порцій — `Meal.nutrition` (MER-79):** ккал і БЖВ Ж і Ч з джерела,
  без множника. Верхні `calories`/БЖВ — порція читання (`mealForPortion`; з
  рядка — Ч); пишеться лише `nutrition`. Профіль без порції — Ч
  (`portionOf`). Немає цифри порції — страва без калорійності.
- **`Meal.source` — підпис плану дієтолога** (не provenance-енум): на ньому
  стоїть мікс; `""` — плану не вказано. `gerd` генератор поки не враховує.

## Генератор тижня

### generateWeek

На слот дня — одна страва: (1) тип збігається; (2) день у коридорі від цілі
(`DEFAULTS`: 2000 ±100 ккал); (3) без повтору у вікні `antiRepeatDays`
(типово 3; понад довжину тижня — «без повторів»), і через межу тижнів;
(4) тиждень міксує плани. Ціль і коридор — з `options.profile`, явні опції
головніші; пул — `generationPool` (`mealIds` у порції профілю).

Пошук (MER-27): день — перебір слотів (вужчі першими) з відсіканням за
залишком суми, тиждень — DFS між днями зі стелями `DAY_*` і
`WEEK_TRIES_PER_CORRIDOR`. Не склалось — коридор ширшає на `CORRIDOR_STEP` до `CORRIDOR_MAX`
(±500); сам `CORRIDOR_MAX` пробується окремо, бо крок може його перестрибнути
(MER-38). Кожне послаблення й single-source-тиждень — у `warnings`, а не
тихий успіх.

`precedingDays` (будує `precedingMealIds`) заповнює вікно антиповтору перед
днем 0: індекс 0 — учора.

### Смаки (MER-18)

Смак — рядок `meal_pref`, не поле страви; правил дієтолога не послаблює.
Улюблені — вага `FAVORITE_WEIGHT` у зваженому перетасуванні (`U^(1/вага)`),
не гарантоване місце. Небажані виключаються першою спробою; без них не
збирається — повний пул і пояснення.

### suggestReplacements / replaceSlot

Кандидат — `valid` + `reasons` (коди `SwapReason`: коридор, повтор в обидва
боки вікна, мікс); UI блокує невалідних (MER-28). Порядок: валідні, не-небажані, улюблені, у
коридорі, без повтору, ближчі до цілі. `replaceSlot` перевіряє лише
цілісність (день, наявний слот, тип): вибір за користувачем.

### mealPlans / isMixedWeek (MER-30)

Належність — множина планів, а не підпис (десерт «Тиждень 1–2» не третій
план): діапазон розгортається до `MAX_PLAN_RANGE`, страва без джерела —
wildcard. Тиждень зміксований ⇔ жоден план не покриває всі його страви; мікс
можливий (`mixPossibleIn`), коли планів ≥ 2 і жоден не покриває весь пул.

## Календар і профіль

**Дата — рядок `YYYY-MM-DD`,** як колонка `date`. `addDays` рахує через
`Date.UTC`: у ніч переведення годинників локальна доба ≠ 24 год (MER-31).
Дат-об'єктів ядро не повертає; розбір ключа один — `dateKeyParts`. Тиждень —
з понеділка.

**`precedingWindow`** = `antiRepeatDays - 1` окремою функцією (у V1 «-1»
губили). День без записів — `[]`: позиція означає «як давно».

**`poolForProfile`:** `mealIds = null` — увесь пул, `[]` — жодної страви;
`generationPool` додає порцію — так пул бачать генератор і нестача пулу.

**`mealTypesFor`:** `withSnack = false` — день без перекусу (MER-78); лише
ці слоти беруть генератор, коридор і `poolShortageFor`. У `PlanDay.meals`
(`DayMeals`) відсутній слот `dayCalories` пропускає, `null` — дірка.
**`planOwnerId`** робить один крок: ланцюжки спільних планів забороняє CHECK.

## rows.ts

SQLite має TEXT, INTEGER, REAL: boolean приходить `1`/`0` (з Postgres —
`true`/`false`), `jsonb` — текстом (або вже масивом). Розбір суворий:
зіпсоване — помилка, не типове значення. Немає boolean-колонки (схема ще не
доїхала) — DEFAULT міграції (`with_snack` — `true`). Порожні кроки рецепта
(артефакт `textarea`) відкидаються. М'яко видалені рядки відсіює запит
викликача.

## Виведені id (sync-ids.ts)

Дві незалежні вставки під частковим унікальним індексом LWW не розсуджує:
друга падає (`23505`, фатально для конектора). Тож пристрої рахують один
UUIDv5 з колонок індексу, і вивантаження стає upsert. Виведений id — лише для
вставки; наявний рядок шукається за природним ключем (`lib/data`,
`lib/powersync`).

- **`MERIDIAN_NAMESPACE` не змінюється ніколи** — «золоті» значення в
  `sync-ids.test.ts` валять тест, а не дані. `uuid` — єдина рантайм-залежність.
- **`derive`** склеює складники через NUL (`SEP` екрановано: живий NUL робить
  файл двійковим для ripgrep); перший — таблиця чи сім'я. Для `shopping.ts`,
  не в барель.

| Функція | Ключ | Чому так |
|---------|------|----------|
| `derivedId` | сім'я, різновид, id V1 | Повторний імпорт оновлює ті самі рядки; профіль V1 `default` однаковий у всіх |
| `mealPrefId` | `meal_id` | Сім'ю вже визначає страва |
| `shoppingCheckId` | сім'я, `item_key`, відбиток | `item_key` — вільний рядок, у сім'ях збігається |
| `planSlotId` | профіль, дата, слот | Без `week_plan_id`: перегенерація переписує ту саму клітинку (MER-49) |
| `recipeId` | `meal_id` | Індекс не частковий: оновлюють будь-який рядок, навіть видалений |
| `familySettingsId` | сім'я | Один рядок на сім'ю |
| `starterMealId` | сім'я, `key` набору | Повторний засів оживляє видалений рядок, а не дублює |

## Список покупок (shopping.ts)

Список не зберігається — щоразу з інгредієнтів слотів. `aggregate` сумує лише
однакові назву й одиницю; без кількості — перелік назв, без «типових»
грамовок; кількість одна на страву, порція її не міняє. Категорія — за точною
назвою з `CATEGORY_BY_NAME` (демо-пул), невідома — «Інше»; `Map`, бо в
об'єкта є `constructor`. `nameKey` лягає в `item_key` позначки — після
першого запису не міняти.

### planFingerprint

Відбиток — «той самий похід у магазин»: позначки фільтруються за ним, а не
стираються (MER-55). Рахується з відсортованих пар «клітинка~страва», не з
`week_plan` (id випадковий). Ручна заміна скидає позначки — список справді
інший. Охоплення не входить. Порожній рядок — плану немає. Під час першої
синхронізації відбиток міняється з чекпоінтами: позначка тих секунд
знімається, повторний дотик її повертає.

## migrateV1

Що не переноситься — `tools/README.md`. Кидає лише на файлі, що не є дампом;
решта — `skipped` із причиною. Некоректне поле відкидає запис, крім кольору
профілю (`FALLBACK_COLOR`); зіпсований рецепт страву не забирає. Id смаку —
`mealPrefId`. `sharedPlanWith` — другим проходом; власник не переїхав —
профіль отримує власний план. Цифри V1 — порція Ч.

## parsePlanText (MER-52)

PDF читає веб (`lib/pdf-text.ts`); береться лише буквальне. Калорії — з
«N ккал»: перший рядок порцій страви («Жінка: N ккал | … | Чоловік: N ккал»
чи «…: Ж - ~N ккал Ч - ~N ккал», MER-139) дає Ж і Ч, число з заголовка слота
(MER-41) — Ч, якщо рядок його не назвав. Підсумки дня, «ккал/добу» й жири
«Ж N г» — ні (тести). БЖВ — ніколи (MER-24). Інгредієнт — лише «число +
г/кг/мл/л»; «Готова порція» — дослівно, до складника; речення з крапкою —
кроки; «На 2-х» — `servings: 2`; назва десерту відрізається на перевірку.
Перенесені рядки склеюються. `kind`: `meal`, `repeat` («Той самий…», не в
пул), `dup` (повтор назви, типово не імпортується). Позначки — коди
`PlanFlag` (текст — `pdf.flag` у вебі).

## Стартовий набір: формат файлу (MER-77)

Страви з планів дієтолога для пулу нової сім'ї. Файл — на сервері **поза
репозиторієм**; підключення — в
[`infra/README.md`](../../infra/README.md#стартовий-набір-страв), вигаданий
приклад — [`infra/starter-set.example.json`](../../infra/starter-set.example.json).
`pnpm starter:check <файл>` — та сама `parseStarterSet`, що перед засівом.
Будь-яка помилка — не засівається нічого; видно до `MAX_ERRORS` помилок
одразу.

Верхній рівень: `{ "version": 2, "meals": [ … ] }`; версія 1 (пласкі
`calories`/БЖВ замість `nutrition`) читається як порція Ч з порожньою Ж. Усі поля страви, крім `macrosApprox`, обов'язкові, **навіть
порожні** (`null`, `[]`, `""`); невідоме — помилка. Межі — як у схемі БД.

| Поле | Тип | Що це |
|------|-----|-------|
| `key` | непорожній, унікальний | Стабільний ключ → id рядка (`starterMealId`). Не змінювати: новий ключ — нова страва |
| `name` | непорожній | Назва |
| `type` | `breakfast`/`lunch`/`dinner`/`snack` | Слот; десерт плану — `snack` |
| `nutrition` | `{ "Ж": {…}, "Ч": {…} }` | `calories` (ціле `>= 0`), `protein`, `fat`, `carbs` (г, `>= 0`); `null` — немає в джерелі |
| `caloriesApprox` | boolean | «≈» на обидві порції (MER-26); `true` без жодної `calories` — помилка |
| `macrosApprox` | boolean | «≈» на БЖВ обох порцій (MER-141), типово `false`; `true` без БЖВ — помилка |
| `ingredients` | масив | Рядок або `{ "name", "amount"?, "unit"? }` |
| `portions` | `{ "component", "text" }[]` | Рядок після «Готова порція:» дослівно (MER-24) |
| `source` | рядок | Підпис плану для міксу; `""` — не вказано |
| `gerd` | boolean | Маркер «ГЕРХ» (MER-75) |
| `sourceIssues` | непорожні рядки | Розбіжності джерела дослівно, без «правильного» значення (MER-76) |
| `recipe` | об'єкт / `null` | `steps` (непорожні рядки), `prepTime` (хв, ціле `>= 0` / `null`), `servings` (ціле `>= 1` / `null`) |

Фото в наборі немає.

### Як засівається

- **Автоматично — раз на сім'ю й лише в порожній пул**
  (`family.starter_seeded_at`); непорожній пул лише позначається.
- **Позначка — після запису страв;** формат і порожнечу перевіряють до нього,
  тож зіпсований чи порожній файл засів не «спалює».
- **Решта — кнопкою «Додати стартовий набір»** на «Стравах»: лише відсутні в
  пулі, без них кнопки немає.
- **Наявних страв засів не переписує** (той самий `key`). Порожній рецепт
  (`hasRecipe`) рядка не створює.

## Тести

`node --test`; Node стирає типи сам: `erasableSyntaxOnly`, імпорти з `.ts`.
`dist` немає (MER-104): `package.json` експортує `src/index.ts`. `typecheck`
проганяє ще `tsconfig.domain.json` без типів Node, тестів, `test-support.ts`
і `check-starter-set.ts`. `weekViolations` перевіряє правила 1–3 на слотах
профілю; мікс — окремими тестами, бо генератор може його послабити.

## Відомі стелі (ponytail)

- **Спільний план тримає коридор лише власника:** генератор і заміна рахують
  у його порції; профіль з іншою порцією бачить свої цифри без коридору.
  Апгрейд — коридор кожного профілю плану в `dayCandidates`.
- **Одна «≈» на обидві порції** — оцінюють цілий план. Апгрейд — колонка
  `calories_w_approx`.
