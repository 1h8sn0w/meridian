# @meridian/core — доменна логіка

Домен чистим TypeScript (MER-47), без фреймворків і БД: той самий код — у
веб, Capacitor і натив. `index.ts` експортує лише те, що імпортує споживач;
модулі й тести імпортують одне одного напряму.

## Модулі

| Модуль | Що робить |
|--------|-----------|
| `types.ts` | Доменна модель: `null` замість NULL, розібраний JSON замість `jsonb` |
| `provenance.ts` | Провенанс, розбір чисел, денна сума |
| `plans.ts` | Належність страви до планів дієтолога, структурно (MER-30) |
| `generator.ts` | Тиждень і достатність пулу (`poolShortageFor`, `poolShortageMessage`) |
| `replace.ts` | Ручна заміна слота (MER-12, MER-28) |
| `calendar.ts` | Дати, антиповтор через межу тижнів (MER-29) |
| `profile.ts` | Пул, порція й слоти профілю, власник спільного плану |
| `rows.ts` | Рядок локального SQLite → доменний об'єкт |
| `sync-ids.ts` | Id, виведені з природного ключа (MER-57) |

## Рішення ядра

- **Жодних сховищ.** Пул, профіль, смаки й минулі дні — аргументи.
- **Випадковість — параметр** (`random`), інакше тиждень не перевірити
  тестом; у тестах — `seeded` (mulberry32) на кількох зернах.
- **Помилка — значення:** `{ ok: true, … }` або `{ ok: false, error }`
  українською. Винятки — лише на зіпсованих даних: рядок (`rows.ts`), число,
  дата, файл не-дамп (`migrateV1`).
- **`calories` nullable.** Генератор і заміна страву без калорій не беруть
  (нуль був би вигадкою) і кажуть про це. У `DayCalories` (похідне, MER-44)
  `unknown` — слоти без цифри, `approx` — є оцінка; неповна сума «≈» не має.
- **Провенанс — кодом, а не колонкою.** `hasValue`: `null`/`undefined`,
  NaN/±∞, порожні рядок і масив — «немає»; нуль і `false` — значення. БЖВ
  видно, якщо є хоч одне з трьох, пропуск — «—». «≈» лише з `caloriesApprox`
  (MER-26), одиницю (`unit`, типово «ккал») дає словник застосунку. `?? 0` у
  ядрі не буває.
- **Цифри порцій — `Meal.nutrition` (MER-79):** ккал і БЖВ Ж і Ч з джерела,
  без множника. Верхні `calories`/БЖВ — порція, в якій страву читають
  (`mealForPortion`; з рядка — Ч); пишеться лише `nutrition`. Профіль без
  порції — Ч (`portionOf`). Немає цифри порції — страва без калорійності.
- **`Meal.source` — підпис плану дієтолога, а не provenance-енум**
  (`'pdf' | 'manual'`): на ньому стоїть мікс. `""` — плану не вказано.
  `gerd` генератор поки не враховує.

## Генератор тижня

### generateWeek

На кожен слот дня — одна страва, так щоб: (1) тип збігався; (2) день був у
коридорі від цілі (`DEFAULTS`: 2000 ±100 ккал); (3) страва не повторювалась у
вікні `antiRepeatDays` (типово 3; понад довжину тижня — «без повторів»),
зокрема через межу тижнів; (4) тиждень міксував плани. Ціль і коридор — із
`options.profile`, явні опції головніші; пул — `generationPool`: підмножина
`mealIds` у порції профілю.

Пошук (MER-27): день — перебір слотів (вужчі першими) з відсіканням за
залишком суми; тиждень — DFS між днями, `DAY_VARIANTS_PER_NODE` варіантів на
вузол, стеля `DAY_PLACEMENTS_PER_TRY`, `WEEK_TRIES_PER_CORRIDOR` спроб на
рівень. Не склалось — коридор ширшає на `CORRIDOR_STEP` до `CORRIDOR_MAX`
(±500); сам `CORRIDOR_MAX` пробується окремо, бо крок може його перестрибнути
(MER-38). Кожне послаблення — у `warnings`, single-source-тиждень — окремим
попередженням, а не тихим успіхом.

`precedingDays` (будує `precedingMealIds`) заповнює вікно антиповтору перед
днем 0: індекс 0 — учора.

### Смаки (MER-18)

Смак — рядок `meal_pref`, не поле страви, і правил дієтолога не послаблює.
Улюблені — вага `FAVORITE_WEIGHT` у зваженому перетасуванні (`U^(1/вага)`),
а не гарантоване місце. Небажані виключаються першою спробою; без них не
збирається — повний пул і пояснення.

### suggestReplacements / replaceSlot

Кандидат — `valid` + `reasons` (коридор, повтор в обидва боки вікна, мікс);
UI блокує невалідних (MER-28). Порядок: валідні, не-небажані, улюблені, у
коридорі, без повтору, ближчі до цілі. `replaceSlot` перевіряє лише
цілісність (день, наявний у дні слот, тип) — вибір за користувачем.

### mealPlans / isMixedWeek (MER-30)

Належність — множина планів, а не підпис (десерт «Тиждень 1–2» не третій
план): діапазон розгортається до `MAX_PLAN_RANGE`, страва без джерела —
wildcard. Тиждень зміксований ⇔ жоден план не покриває всі його страви; мікс
можливий (`mixPossibleIn`), коли планів ≥ 2 і жоден не покриває весь пул.

## Календар і профіль

**Дата — рядок `YYYY-MM-DD`,** як колонка `date`. `addDays` рахує через
`Date.UTC`: у ніч переведення годинників локальна доба ≠ 24 год (MER-31).
Дат-об'єктів ядро не повертає; розбір ключа один — `dateKeyParts`. Тиждень — з понеділка.

**`precedingWindow`** = `antiRepeatDays - 1` окремою функцією: у V1 «-1» на
місці виклику загубили. День без записів — `[]`, бо позиція означає «як
давно».

**`poolForProfile`:** `mealIds = null` — увесь пул, `[]` — жодної страви;
`generationPool` додає порцію — так пул бачать генератор і нестача пулу.

**`mealTypesFor`:** `withSnack = false` — день без перекусу (MER-78); лише
ці слоти беруть генератор, коридор і `poolShortageFor`. `PlanDay.meals` —
`DayMeals`: відсутній слот `dayCalories` пропускає, `null` — дірка.
**`planOwnerId`** робить один крок: ланцюжки спільних планів забороняє CHECK.

## rows.ts

SQLite має TEXT, INTEGER, REAL: boolean приходить `1`/`0` (з Postgres —
`true`/`false`), `jsonb` — текстом (або вже масивом). Розбір суворий:
зіпсоване — помилка, не значення за замовчуванням. Рядок без boolean-колонки
(схема ще не доїхала) — DEFAULT міграції (`with_snack` — `true`). Порожні кроки
рецепта — артефакт `textarea`, відкидаються. М'яко видалені рядки відсіює
запит викликача.

## Виведені id (sync-ids.ts)

Дві незалежні вставки під частковим унікальним індексом LWW не розсуджує:
друга падає (`23505`, фатально для конектора). Тому пристрої рахують один
UUIDv5 із колонок індексу, і вивантаження стає upsert. Виведений id — лише для
вставки: наявний рядок шукається за природним ключем (див.
`apps/web/src/lib/data`, `lib/powersync`).

- **`MERIDIAN_NAMESPACE` не змінюється ніколи** — «золоті» значення в
  `sync-ids.test.ts` валять тест, а не дані. `uuid` — єдина рантайм-залежність.
- **`derive`** склеює складники через NUL (`SEP` екрановано: живий NUL робить
  файл двійковим для ripgrep). Перший складник — таблиця чи сім'я. Для
  `shopping.ts`, не в барель.

| Функція | Ключ | Чому так |
|---------|------|----------|
| `derivedId` | сім'я, різновид, id V1 | Повторний імпорт оновлює ті самі рядки; профіль V1 `default` однаковий у всіх |
| `mealPrefId` | `meal_id` | Сім'ю вже визначає страва |
| `shoppingCheckId` | сім'я, `item_key`, відбиток | `item_key` — вільний рядок, у сім'ях збігається |
| `planSlotId` | профіль, дата, слот | Без `week_plan_id`: перегенерація переписує ту саму клітинку (MER-49) |
| `recipeId` | `meal_id` | Індекс не частковий: будь-який наявний рядок, навіть видалений, оновлюють |
| `familySettingsId` | сім'я | Один рядок на сім'ю |
| `starterMealId` | сім'я, `key` набору | Повторний засів оживляє видалений рядок, а не дублює |

## Список покупок (shopping.ts)

Список не зберігається — щоразу з інгредієнтів слотів. `aggregate` сумує лише
однакові назву й одиницю; без кількості — перелік назв, «типових» грамовок
немає; кількість одна на страву, порція її не міняє. Категорія — за точною назвою з
`CATEGORY_BY_NAME` (назви демо-пулу), невідома — «Інше»; `Map`, бо в об'єкта є
`constructor`. `nameKey` лягає в `item_key` позначки — після першого запису не
міняти.

### planFingerprint

Відбиток — «той самий похід у магазин»: позначки фільтруються за ним, а не
стираються (MER-55). Рахується з відсортованих пар «клітинка~страва», а не з
`week_plan` (випадковий id, різний між пристроями). Ручна заміна скидає
позначки — список справді інший. Охоплення не входить. Порожній рядок —
плану немає. Під час першої синхронізації відбиток міняється з чекпоінтами:
позначка тих секунд знімається, повторний дотик її повертає.

## migrateV1

Що не переноситься — `tools/README.md`. Кидає лише на файлі, що не є
дампом; решта — `skipped` із причиною. Некоректне поле відкидає запис, крім
кольору профілю (`FALLBACK_COLOR`). Зіпсований рецепт страву не забирає. Id
смаку — `mealPrefId`. `sharedPlanWith` — другим проходом; власник не
переїхав — профіль отримує власний план. Цифри V1 — порція Ч.

## parsePlanText (MER-52)

PDF читає веб (`lib/pdf-text.ts`). Береться лише буквальне: калорії — з
«N ккал», і в заголовку слота (MER-41), у порцію Ч; БЖВ — ніколи («Ж»/«Ч» —
порції, MER-24); інгредієнт — лише з «число + г/кг/мл/л»; «Готова порція» —
дослівно, прив'язана до складника; речення з крапкою — кроки; «На 2-х» —
`servings: 2`; назва десерту відрізається й позначається на перевірку.
Перенесені рядки склеюються. `kind`: `meal`; `repeat` («Той самий…», у пул не йде); `dup` (назва
вже була, типово не імпортується). Результат — кандидати поруч із сирим текстом.

## Стартовий набір: формат файлу (MER-77)

Страви з планів дієтолога для засіву пулу нової сім'ї. Файл — на сервері
**поза репозиторієм**; підключення — в
[`infra/README.md`](../../infra/README.md#стартовий-набір-страв), вигаданий
приклад — [`infra/starter-set.example.json`](../../infra/starter-set.example.json).
`pnpm starter:check <файл>` — та сама `parseStarterSet`, що перед засівом.
Будь-яка помилка — не засівається нічого; показуються до `MAX_ERRORS` помилок
одразу.

Верхній рівень: `{ "version": 2, "meals": [ … ] }`. Версія 1 (пласкі
`calories`/`protein`/`fat`/`carbs` замість `nutrition`) читається як порція Ч
з порожньою Ж. Усі поля страви
обов'язкові, **навіть порожні** (`null`, `[]`, `""`); невідоме поле — помилка.
Межі — як у схемі БД.

| Поле | Тип | Що це |
|------|-----|-------|
| `key` | непорожній, унікальний | Стабільний ключ → id рядка (`starterMealId`). Не змінювати: новий ключ — нова страва |
| `name` | непорожній | Назва |
| `type` | `breakfast`/`lunch`/`dinner`/`snack` | Слот; десерт плану — `snack` |
| `nutrition` | `{ "Ж": {…}, "Ч": {…} }` | Порція: `calories` (ціле `>= 0` / `null`), `protein`, `fat`, `carbs` (г, `>= 0` / `null`). `null` — немає в джерелі |
| `caloriesApprox` | boolean | «≈» на обидві порції (MER-26); `true` без жодної `calories` — помилка |
| `ingredients` | масив | Рядок або `{ "name", "amount"?, "unit"? }` |
| `portions` | `{ "component", "text" }[]` | Рядок після «Готова порція:» дослівно (MER-24) |
| `source` | рядок | Підпис плану для міксу; `""` — не вказано |
| `gerd` | boolean | Маркер «ГЕРХ» (MER-75) |
| `sourceIssues` | непорожні рядки | Розбіжності джерела дослівно, без «правильного» значення (MER-76) |
| `recipe` | об'єкт / `null` | `steps` (непорожні рядки), `prepTime` (ціле `>= 0` / `null`, хв), `servings` (ціле `>= 1` / `null`) |

Фото в наборі немає — лише від користувача.

### Як засівається

- **Автоматично — раз на сім'ю й лише в порожній пул**
  (`family.starter_seeded_at`). Стара сім'я з непорожнім пулом лише
  позначається.
- **Позначка — після запису страв;** формат і порожнечу перевіряють до нього,
  тож зіпсований файл засів не «спалює».
- **Решта — кнопкою «Додати стартовий набір»** на «Стравах»: видна, коли в
  наборі є відсутні в пулі страви, і додає лише їх.
- **Наявних страв засів не переписує:** той самий `key` лишається як є.
  Порожній рецепт (`hasRecipe`) рядка не створює.

## Тести

`node --test`; Node стирає типи сам: `erasableSyntaxOnly`, імпорти з `.ts`.
`dist` немає (MER-104): `package.json` експортує `src/index.ts`. `typecheck`
проганяє ще `tsconfig.domain.json` без типів Node, тестів, `test-support.ts`
і `check-starter-set.ts`. `weekViolations` перевіряє правила 1–3 на слотах
профілю; мікс — окремі тести: генератор може свідомо його послабити.

## Відомі стелі (ponytail)

- **Спільний план тримає коридор лише власника:** генератор і заміна рахують
  у його порції; профіль з іншою порцією бачить свої цифри без оцінки
  коридору. Апгрейд — коридор кожного профілю плану в `dayCandidates`.
- **Одна «≈» на обидві порції** — оцінюють цілий план. Апгрейд — колонка
  `calories_w_approx`.
