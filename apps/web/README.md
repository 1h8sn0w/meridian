# @meridian/web — застосунок

Статичний SPA: Vite + TanStack Router. Сервера застосунку немає — `index.html`
і бандли віддає Caddy стека як звичайні файли, а ту саму збірку загортає
Capacitor (ADR 001). Тож серверного в екранах немає й бути не може: усе, що
вміє застосунок, він уміє з локальної бази на пристрої.

`vite.config.ts` зібрано за офіційною інструкцією TanStack Router для Vite
(плагін `tanstackRouter` перед плагіном React), без власних надбудов. Загальну
документацію TanStack цей файл не переказує: нижче лише те, що стосується
Meridian.

## Запуск

Застосунок розрахований на піднятий поруч стек — він бере ту саму базу, той
самий GoTrue і той самий sync, лише з гарячою заміною модулів:

```bash
docker compose up -d          # з кореня репозиторію
cp apps/web/.env.example apps/web/.env
pnpm dev                      # http://localhost:3000
```

`pnpm dev` працює і з кореня, і з `apps/web`: `@meridian/core` приходить через
`workspace:*` вихідними `.ts`, збирати його заздалегідь не треба (MER-104).

`.env` потрібен тому, що `pnpm dev` — це Vite поза стеком: змінні він
підставляє на етапі збірки, а anon-ключ генерується всередині стека, тож
вписувати його нема звідки. Готовий файл робиться однією командою — вона в
[`.env.example`](.env.example).

Без пари `PUBLIC_SUPABASE_*` застосунок показує явний екран «не налаштовано», а
не ламається мовчки. Без `PUBLIC_POWERSYNC_URL` він повноцінний, просто
лишається на одному пристрої — і панель синхронізації каже це прямо.

## Публічний конфіг береться рантаймом (MER-45)

Браузер ходить у Supabase сам, тож йому потрібні адреса проєкту, anon-ключ і
адреса sync. У стеку їх вписує в `index.html` **Caddy, на кожній відповіді** —
директивою `templates` ([`infra/caddy/Caddyfile`](../../infra/caddy/Caddyfile)),
зі свого оточення (`compose.yaml`). Тому один образ їде на будь-який self-host
без перезбірки, і заповнювати не треба нічого.

Там, де шаблон ніхто не заповнює — dev-сервер Vite, `pnpm preview`, Capacitor, —
він лишається літералом `{{…}}`, і `src/lib/public-env.ts` бере значення,
запечені Vite із `PUBLIC_*`. Звідси правило для веб-образу: **`PUBLIC_*` під час
його збірки не задавати.** Запечене значення перебило б те, що прийшло
рантаймом; докер-контекст `.env` і так не бачить (`.dockerignore`).

## Що де лежить

| Шлях | Що |
|------|-----|
| `index.html` | Розмітка сторінки, PWA-мети й шаблон публічного конфігу |
| `src/main.tsx` | Вхід: роутер, провайдери входу й синхронізації, реєстрація воркера |
| `src/routes` | Маршрути (MER-49, MER-61…63): `/` — «Сьогодні», `/week`, `/calendar`, `/meals`, `/recipe/$mealId`, `/shopping`, `/family` |
| `src/components` | Екрани й спільні елементи, дизайн «Сонячна дуга» ([README](src/components/README.md)) |
| `src/lib` | Логіка пристрою: вхід, годинник дня, нагадування, стартовий набір ([README](src/lib/README.md)) |
| `src/lib/data` | Читання (`queries.ts`) і записи (`mutations.ts`) локальної бази ([README](src/lib/data/README.md)) |
| `src/lib/powersync` | Клієнтська схема, конектор до Supabase, життєвий цикл React ([README](src/lib/powersync/README.md)) |
| `src/styles.css` | Єдиний Tailwind у репозиторії (MER-53): токени в `@theme`, без preflight |
| `public` | Маніфест, іконки та service worker (MER-51) — віддаються як є |

Вкладок у таб-барі п'ять: рецепт відкривається зі страви, а список покупок відкривається з
«Тижня» — він збирається з інгредієнтів саме того плану і без плану порожній.

Доменної логіки тут немає — генератор, калорії й провенанс живуть у
[`packages/core`](../../packages/core).

## Локальна база (MER-46, MER-49)

Джерело істини для інтерфейсу — SQLite на пристрої: екрани читають реактивними
запитами й не чекають мережі ніколи. Читання й записи —
[`src/lib/data`](src/lib/data/README.md), синхронізація на пристрої —
[`src/lib/powersync`](src/lib/powersync/README.md), серверні правила —
[`infra/powersync`](../../infra/powersync/README.md).

## Стилі (MER-53)

**Tailwind у репозиторії рівно один — тут.** Збирає його офіційний плагін
`@tailwindcss/vite`, точка входу — `src/styles.css`. Окремого кроку збірки CSS
немає: `pnpm dev` і `pnpm build` роблять усе самі. Стару збірку V1 через
`@tailwindcss/cli` із закоміченим `tailwind.css` прибрано разом зі скриптами
`build:css` / `watch:css`. Не відроджувати її й не додавати Play CDN, PostCSS
чи JS-конфіг: у Tailwind v4 конфігурація живе в CSS.

- **Дизайн-токени — у `@theme`** в `src/styles.css`. Токени, що посилаються на
  інші CSS-змінні (колір активного профілю), — у `@theme inline`, інакше
  utility-клас підставить посилання на змінну замість її значення.
- **Preflight свідомо вимкнено**, щоб не змінювати нативний вигляд form
  controls. Замість повного `@import 'tailwindcss'` шари імпортуються явно, і
  рядок з `preflight.css` пропущено. Потрібні reset-властивості оголошені в
  шарі `base`.
- **`source(none)` і `@source` не використовувати.** Автовизначення джерел
  стартує з `apps/web` і само ігнорує `node_modules`, ігнороване git'ом і
  бінарники.
- Правило значень (без arbitrary values) — в `AGENTS.md`, правила дизайну —
  у [`src/components/README.md`](src/components/README.md#дизайн-сонячна-дуга).
  Після заміни typography-токенів перевіряти браузером line-height,
  переповнення на мобільній ширині й межі responsive-breakpoint.

## PWA і офлайн (MER-51)

Дані офлайну не потребують уже давно — екрани читають базу на пристрої. Тут
лише оболонка: маніфест, іконки й service worker лежать у `public/` і їдуть у
збірку як є.

Воркер реєструється **лише в прод-збірці** (`import.meta.env.PROD`): у
`pnpm dev` кешована оболонка коштувала б дорожче за користь — і потім довго
пояснювала б собою «чому зміни не видно».

- **Кешується тільки оболонка й тільки за білим списком**: шляхи `/assets/`,
  `/icons/`, маніфест — і навігація, але лише коли відповідь `text/html`.
  Supabase і PowerSync у продакшні стоять на тому самому походженні, тож чорний
  список рано чи пізно поклав би в кеш чужу сесію або чужий JSON, а вкладка,
  відкрита руками на `/rest/v1/`, зробила б офлайн-стартом застосунку JSON.
- **Оболонка лежить під одним ключем `/` на всі адреси.** `index.html` один на
  всі маршрути, маршрут визначає роутер з адреси.
- **`/` і файли збірки кладуться в кеш на `install`.** Свою ж навігацію воркер
  не перехоплює, тож без цього оболонка з'явилась би в кеші лише з другого
  завантаження. Імена файлів збірки з хешем воркер бере з самого HTML, який
  щойно поклав.
- **Кладемо по одному (`cache.add` + `allSettled`), а не `addAll`.** Той
  усе-або-нічого: одна невдала іконка лишила б пристрій без оболонки, причому
  мовчки — `register()` про провал `install` не дізнається.
- **Версію кеша піднімати й тоді, коли змінився ВМІСТ файлів `SHELL`** (іконка,
  маніфест): воркер, що не змінився байтами, браузер не перевстановлює.
  Звичайна зміна застосунку бампа не потребує.
- **`viewport-fit=cover` свідомо НЕ ставимо.** Він розтягує viewport під
  вирізи, і безпечні поля довелося б відбивати руками з усіх боків — зокрема
  згори, де липка шапка лягла б під системну смугу.
- Прекешу всіх чанків збірки немає, як і прибирання старих: у кеш потрапляють
  лише маршрути, які встигли завантажитись онлайн, а кожен деплой додає новий
  набір імен поверх старого. Обидва кінці лікує список імен зі збірки, тобто
  плагін збірки, — додати, коли почне заважати.

Перевірити офлайн: `pnpm build && pnpm preview`, відкрити застосунок, зупинити
`preview` і перезавантажити сторінку — має з'явитись та сама оболонка.

## Прод-збірка

```bash
pnpm build      # dist/ — статичні файли, більше нічого
pnpm preview    # роздати dist/ локально (конфіг — із запечених PUBLIC_*)
```

У стеку `dist/` лежить усередині образу Caddy
([`infra/web.Dockerfile`](../../infra/web.Dockerfile)) — окремого контейнера під
застосунок немає. Адреси маршрутів (`/week`, `/recipe/…`) Caddy віддає тим самим
`index.html` (`try_files`), а далі маршрут веде роутер у браузері.

## Нативна оболонка Capacitor (MER-50)

> **Не перевірено на пристрої.** Обгортку зібрано, платформи згенеровано, але
> жодного разу не скомпільовано в `.apk`/`.ipa` й не запущено на телефоні чи
> емуляторі: на машині, де це робилось, немає ні JDK з Android SDK, ні macOS з
> Xcode. Усе нижче — інструкція й каркас, а не звіт про робочу збірку. Перший,
> хто матиме SDK, має пройти її вручну й виправити те, що не зійдеться.

Навіщо: у вебі локальний SQLite лежить в OPFS/IndexedDB, а iOS витирає їх за
LRU, коли бракує місця, — застосунок, у який тиждень не заходили, може
відкритися порожнім. Нативний SQLite такому не підлягає. Другим кроком це ще й
ґрунт для справжніх push-нагадувань замість вебових (MER-65).

```bash
pnpm build:native        # vite build --mode native → dist/
npx cap sync             # копіює збірку в android/ та ios/, оновлює плагіни
npx cap open android     # Android Studio
npx cap open ios         # Xcode (лише macOS)
```

Потрібне (нічого з цього не потрібно для вебу): для Android — JDK 21 і Android
SDK (простіше через Android Studio); для iOS — macOS, Xcode і CocoaPods.
`npx cap add` натомість SDK не потребує: він лише розкладає шаблон проєкту, тож
каталоги `android/` та `ios/` створені й закомічені звідси, з Windows.

Два наслідки, про які треба знати наперед:

- **Вебзбірка й нативна — той самий статичний `dist/`.** Відколи веб теж
  статичний, різниця лише в режимі: `--mode native` перемикає драйвер SQLite
  (нижче). Окремого «домальовування каркаса» більше не існує.
- **`PUBLIC_*` для нативної збірки беруться з оточення ЗБІРКИ, не рантайму.**
  У телефоні немає Caddy, який заповнив би шаблон конфігу в `index.html`, тож
  застосунок бере запечені значення. Це протилежно вебу (MER-45), і інакше не
  буває: у `.apk` немає кому підставити адреси потім. Зібрати без них —
  отримати всередині телефону сторінку «не налаштовано».

Драйвер SQLite обирається на етапі збірки, у `lib/powersync/db.ts`:
`@powersync/capacitor` статично тягне `@capacitor/core` і
`@capacitor-community/sqlite`, тож у вебзбірку йому не можна. Гілка стоїть під
константою `import.meta.env.MODE`, і у вебі мертва гілка разом з її `import()`
вирізається — перевірено: у `dist` звичайної збірки нативних пакетів немає.
Клас той самий (`PowerSyncDatabase` з тими самими опціями), різниця лише в
адаптері: на iOS/Android — нативний SQLite замість wa-sqlite у WASM.

`@powersync/capacitor` тримається на `0.8.x` навмисно: `0.9.0` вимагає
`@powersync/web` ≥ 2.3, а це підняло б ядро синхронізації робочого вебу заради
недоведеної нативної гілки. Сам пакет автор помітив як `@experimental`.

Окремо не перевірено (крім самої збірки): чи реєструється service worker
(MER-51) у webview — на `capacitor://` їх немає, і реєстрація там просто впаде в
`catch`; чи не конфліктує його кеш навігації зі статичним `index.html`.

## Перевірки

```bash
pnpm lint
pnpm typecheck   # tsc --noEmit
pnpm test
```

Форматування — спільне й перевіряється з кореня: `pnpm format:check`.

`src/routeTree.gen.ts` генерує плагін роутера під час `pnpm dev` і `pnpm build`.
Файл машинний, у Prettier ігнорований, але **комітиться**: додали маршрут —
запустіть перед комітом одне з двох, інакше `typecheck` не знайде маршрут у
дереві. Окремого кроку генерації в `typecheck` більше немає, тож і холостої
зміни цього файлу на кожному запуску теж.

### Чому `tsconfig.json` не розширює кореневий (MER-71)

Сім опцій (`target`, `strict`, `noUnusedLocals`, `noUnusedParameters`,
`noFallthroughCasesInSwitch`, `skipLibCheck`, `verbatimModuleSyntax`) справді
повторюють `tsconfig.base.json`. Але база — **для ядра**: крім них вона
задає `module`/`moduleResolution` `NodeNext` (застосунку потрібен `bundler`),
`lib` без DOM, `isolatedModules` і `noUncheckedIndexedAccess`, а
`noUncheckedIndexedAccess` тут не діє свідомо (`lib/data/model.ts` покладається
на це). Тобто `extends` довелося б супроводжувати перевизначеннями —
файл став би довшим за той, що є, і крихкішим: правка бази мовчки міняла б
строгість перевірки застосунку. Тому дублювання семи рядків лишається навмисно.

ESLint — інша річ: там спільна частина без побічних ефектів, і вона винесена в
кореневий `eslint.config.base.mjs`.
