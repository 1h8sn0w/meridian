# lib/powersync — синхронізація на пристрої

Клієнтський бік синхронізації (MER-46): локальний SQLite, конектор до Supabase
і життєвий цикл у React. Серверні правила (які таблиці, ключ сім'ї, доставка
видалень) описано в [`infra/powersync/README.md`](../../../../../infra/powersync/README.md).

| Файл | Що |
|------|-----|
| `schema.ts` | Клієнтська схема `AppSchema`, `JSON_COLUMNS`, `BOOLEAN_COLUMNS` |
| `db.ts` | Відкриття бази, вибір драйвера SQLite, черга операцій `enqueue` |
| `connector.ts` | Токен для PowerSync і вивантаження записів через PostgREST |
| `provider.tsx` | Життєвий цикл бази в React і стан синхронізації для екранів |
| `sync-contract.test.ts` | Збіг міграцій, `sync-config.yaml` і клієнтської схеми |

## Тверді правила

- **Джерело істини для інтерфейсу — локальний SQLite.** Читання й записи не
  чекають мережі ніколи; PowerSync фоном тримає базу в збіжності з Postgres.
- **Записи йдуть через PostgREST, а не «в PowerSync».** Звідси LWW: конкурентні
  зміни — це два звичайні UPDATE, і перемагає той, що прийшов останнім.
- **Часові позначки пише сервер.** Конектор викидає `created_at`/`updated_at` з
  вивантаження, інакше порядок LWW залежав би від годинника телефона.
- **Типи на межі вивантаження конвертуються назад.** У SQLite типів три, тож
  `jsonb` лежить на пристрої рядком, а `boolean` — числом 0/1. PostgREST кладе
  значення в колонку як є, тож без зворотного перетворення JSON-рядок стає
  jsonb-РЯДКОМ, і сервер відкидає запис на `jsonb_typeof(...) = 'array'`
  (MER-49). Нова така колонка дописується в `JSON_COLUMNS` або
  `BOOLEAN_COLUMNS` тим самим рухом, що й у таблицю.
- **PUT у конекторі дописує `deleted_at: null`.** Вставка — це живий рядок за
  визначенням, а з виведеним id (`packages/core/src/sync-ids.ts`, MER-57) вона
  може потрапити на власний м'яко видалений рядок на сервері. Upsert оновлює
  лише передані колонки, і без цього позначка видалення тихо лишилася б.
- **Операції з базою серіалізуються** (`enqueue` у `db.ts`). `connect`,
  `disconnect` і `disconnectAndClear` беруть внутрішні блокування, і запущені
  паралельно лишають базу відкритою, але незʼєднаною — назавжди.
- **`@powersync/web` вантажиться лише динамічно, з ефекту.** У ньому WASM і
  web-workers. Драйвер SQLite обирається на етапі збірки (веб чи Capacitor,
  `apps/web/README.md`), і динамічний імпорт дає викинути мертву гілку. Заразом
  база не вантажиться, доки немає сім'ї, якій вона належить.
- **База пристрою відкривається завжди, з'єднання — лише за наявності адреси
  сервісу.** Без `PUBLIC_POWERSYNC_URL` застосунок повноцінний, просто лишається
  на одному пристрої, і панель синхронізації каже це прямо.

## Збіг схеми в чотирьох місцях

Міграції, `sync-config.yaml`, `AppSchema` і `JSON_COLUMNS`/`BOOLEAN_COLUMNS`
звіряє `sync-contract.test.ts`; таблиця, що свідомо не їде на пристрої, — у
його винятках (`NOT_PUBLISHED`). Що змінювати при новій таблиці —
[`packages/db/README.md`](../../../../../packages/db/README.md#якщо-додаєте-таблицю).

У розробці база лежить ще й на `window.Meridian.sync`: запит із консолі —
найкоротший спосіб перевірити, що зміна доїхала до сервера й на інший пристрій.
У прод-збірці гілка вирізається цілком (`import.meta.env.DEV`).

## Відомі стелі (ponytail)

- `sync-contract.test.ts` читає SQL регулярками, інструкцію за інструкцією й
  без огляду на регістр: `CREATE`/`DROP TABLE`, `ADD`/`DROP COLUMN`,
  `FOR`/`ADD`/`SET`/`DROP TABLE` публікації й `GRANT`/`REVOKE … ON TABLE` для
  `powersync_role`. Незнайома форма `CREATE`/`DROP TABLE`, публікації чи гранту
  валить тест. Мовчки він не бачить `RENAME`, `ALTER COLUMN … TYPE` і DDL
  усередині `DO`-блоків (крім публікації). Масив Postgres на пристрої — JSON,
  тож тест вимагає його в `JSON_COLUMNS`. Перша міграція поза цим — сигнал
  навчити тест або звіряти схему з живою базою в CI.
