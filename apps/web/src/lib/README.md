# lib — логіка застосунку поза екранами

Доменної логіки тут немає: генератор, калорії й провенанс живуть у
[`packages/core`](../../../../packages/core/README.md). Тут те, що належить
пристрою й браузеру. Підтеки мають свої README:
[`data`](data/README.md) (читання й записи бази),
[`powersync`](powersync/README.md) (синхронізація) і
[`i18n`](i18n/README.md) (мова інтерфейсу, словники).

| Модуль | Що |
|--------|-----|
| `auth.tsx` | Стан входу й сім'ї: сесія GoTrue, claim `family_id` |
| `supabase.ts` | Один клієнт Supabase на вкладку |
| `oauth.ts` | Вхід і прив'язка Google, Discord, GitHub |
| `public-env.ts` | Публічний конфіг рантаймом ([`apps/web`](../../README.md#публічний-конфіг-береться-рантаймом-mer-45)) |
| `day-clock.ts` | Вікна прийомів їжі, їх валідація й геометрія годинника дня |
| `meal-windows.tsx` | Вікна сім'ї з `family_settings` для всього застосунку (`useMealWindows`) |
| `use-now.ts` | Одне «зараз» на весь застосунок |
| `reminders.ts` | Нагадування перед прийомами: розклад, текст, налаштування |
| `starter-set.ts` | RPC стартового набору й порядок кроків засіву |
| `pdf-text.ts` | Текстовий шар PDF через pdf.js |
| `active-profile.ts`, `shopping-scope.ts`, `shopping-period.ts`, `device-choice.ts` | Вибір, що належить пристрою, а не сім'ї |
| `forms.ts` | Чернетки й валідація форм |
| `format.ts`, `messages.ts`, `meal-text.ts` | Дати й числа мовою інтерфейсу, помилки, інгредієнти й порції ↔ текст форми |
| `calendar-search.ts`, `meals-search.ts` | Стан «Календаря» й фільтри «Страв» в адресі |
| `shopping-share.ts`, `week-share.ts`, `recipe-share.ts`, `share.ts` | Покупки, меню й рецепт текстом, «поділитися або скопіювати» |
| `scroll-catch-up.ts` | Догнати прокрутку, яку роутер не встиг відновити |
| `wake-lock.ts` | Екран не гасне, поки відкрито рецепт |

Модулі без React (`reminders.ts`, `messages.ts`, …) імпортують сусідів із
`.ts`: `node --test` стирає типи, але не переписує шляхів.

## Вибір пристрою

`useStoredChoice` (`device-choice.ts`) — сховище в `localStorage`, читається
синхронно до першого рендеру; `null` стирає ключ, щоб сентинел не лежав
рядком поруч з id. Самозцілення в кожного своє:

- **`useActiveProfile`**: збережений id зник (профіль видалили на іншому
  пристрої) — перший профіль, і це **записується**, щоб пережити
  перезавантаження. `applyAccent` ставить лише `--accent`; прозорий варіант —
  `color-mix` у CSS. `ownerCorridorApplies` — порція профілю збігається з
  порцією власника плану, тож коридор плану про його цифри.
- **`useShoppingScope`**: зниклий профіль — «усі», і це **не записується**:
  «усі» — це відсутність ключа. Краще показати більше, ніж нічого.
- **`useShoppingPeriod`**: так само, невідоме — «увесь план» без ключа. Дні
  відбирає `inShoppingPeriod`, межі — у тестах.
- `useNow`: такт 30 с, значення є з першого кадру.

## auth.tsx

**Сесія живе на пристрої, а сервера застосунку немає.** Вхід робить браузер
через `@supabase/supabase-js`. Стан входу перевіряється один раз у кореневому
маршруті (`AppGate`), і лише «увійшли й сім'я є» пускає до маршрутів
застосунку.

- **Після зміни членства обов'язковий `refreshSession()`.** Старий токен ще без
  claim `family_id`, і застосунок бачитиме порожньо.
- `onAuthStateChange` сам віддає `INITIAL_SESSION`, окремий `getSession()` не
  потрібен; у колбеку — лише `setState` (вимога документації Supabase).
  `SIGNED_OUT` гасить `linkReturn`: інакше наступний акаунт побачив би чужу
  прив'язку.
- Сім'я, склад і запрошення читаються без фільтра `family_id`: вибірку звужує
  RLS. Відповіді для сім'ї, що встигла змінитись, відкидаються.
- Інший `familyId` скидає сім'ю, склад і запрошення в рендері
  (`shownFamilyId`), а не в ефекті.
- `signUp` → `false`: сесії немає, GoTrue чекає підтвердження пошти. Термін
  запрошення береться з бази, а не рахується тут.
- **Запрошення — кодом, не листом:** self-host без SMTP листа не надішле. Правила БД для членства —
  [`packages/db/README.md`](../../../../packages/db/README.md).

## supabase.ts

Один клієнт на вкладку: другий незалежно оновлював би той самий
refresh-токен. Сесія — у `localStorage`;
PKCE: повернення з `?code=` клієнт обмінює сам, якщо в сховищі є
верифікатор, тож чужий `code` в адресі не чіпає.
`familyIdFromToken` читає claim без перевірки підпису: це підказка
інтерфейсу, доступ вирішує Postgres.

## oauth.ts

- Кнопки — лише для `true` у `external` з `/auth/v1/settings`; збій запиту —
  екран як без OAuth. Помилку повернення (`?error_code=`) віддає
  `initialize()`, `redirectError` бере код із `details` для `authFailure`.
  `withoutRedirectError` прибирає її з адреси (supabase-js чистить лише
  `code`).
- Пошти може не бути (Discord без `email`): `auth.tsx` пише `''` як `null`.
- Прив'язка (`startLink`) вертає на `/family`; позначка в `sessionStorage`
  каже `auth.tsx`, що повернення — з прив'язки (`linkReturn`), а не вхід.
  Що не відв'язується — тести `signInMethods`.
- `redirectFailure` гасне з сесією, `linkReturn` — з переходом на інший шлях
  (`dismissReturnNotices` в `AppGate`).

## messages.ts

Перекладаємо те, що людина може виправити; решту — загальний текст плюс
оригінал для того, хто піднімав self-host. Правила
`localDbFailure` і `syncFailure` — у `messages.test.ts`: помилки PowerSync
приходять із воркера лише текстом, тож мережа й «вхід не прийнято»
впізнаються регулярками. `rejectionFailure`
називає таблицю й причину відмови сервера за кодом Postgres; невідомі —
загально, код і текст сервера — у деталях. `Outcome` — свій тип, не
`Result` ядра: одне ім'я на два типи — пастка.

## format.ts, meal-text.ts

- «Чи показувати» й «≈» вирішує ядро (`formatCalories`, `hasMacros`), тут —
  лише як. Ключ дати розбирає `dateKeyParts` ядра.
- `formatMoment`: `timestamptz` у SQLite — текст двох форм (пристрій — ISO,
  реплікація — з пробілом); нечитане — порожній рядок.
- `meal-text.ts` нічого не добудовує: без кількості — без `amount`/`unit`.
  Поле форми пише кількість `String` (без розрядів, однаково в усіх мовах),
  показ — мовою інтерфейсу; розбір читає й «1 500 г».

## calendar-search.ts, meals-search.ts

Невідоме значення з адреси — «без параметра»; дата мусить існувати,
тиждень вирівнюється на понеділок.

## shopping-share.ts

Текст — той самий список, що на екрані: лише некуплене, кількість лише з
джерела, без неї — окремим блоком, свої пункти — останнім. Порожній текст —
кнопки немає.

## recipe-share.ts

`recipeText` — назва, склад як у формі, кроки з номерами; ні складу, ні
кроків — порожньо.

## week-share.ts, share.ts

`weekMenuText` — дні плану від сьогодні, «прийом — страва», видалена —
`mealRemoved`; минули всі — порожньо, кнопки немає. Календар дає один
вибраний день, минулий — без кнопки.

### shareOrCopy

Меню — лише коли `canShare` приймає дані; закрите — `cancelled`, інша
відмова — буфер; без API — `failed` (`common.shareFailed`).

## scroll-catch-up.ts

`catchUpScroll` докручує, щойно документ виростає, до цілі (допуск 1 px). Відступає на `pointerdown`/`keydown`/`wheel` (не `scroll`: його
викликає й наш `scrollTo`) або коли позиція вища за нашу й не внизу — людина
гортає смугою.

## day-clock.ts

**Вікна прийомів їжі — налаштування сім'ї, а не правило дієтолога**, тому
живуть тут, а не в `packages/core`. Сім'я задає сніданок, обід і вечерю
(`MealHours`, `family_settings`); без налаштування —
`DEFAULT_MEAL_HOURS` із V1. Перекус — завжди проміжок
між кінцем обіду й початком вечері; обід упритул до вечері лишає перекус без
вікна. З тих самих вікон `slotAt` бере фазу неба (`components/Sky.tsx`),
активну страву на «Сьогодні» і розклад нагадувань (ці два — лише слоти плану,
`windowsInPlan`), тож функції беруть вікна аргументом.

- **Валідація одна — `mealHoursProblems`**: її показує форма біля поля, нею ж
  `mealHoursFromRow` відкидає битий рядок (тоді діють стандартні вікна, а
  екран показує попередження). Ті самі межі тримають CHECK-и бази.
- `MealWindow` не має підпису: назва прийому — `common.mealType` словника.
- **`useMealWindows` працює й без бази**: поза провайдером чи до відкриття
  бази (екран входу) — стандартні вікна. Базу читає сусід `StoredMealHours`,
  а не обгортка `children` (чому — `SyncProvider` у `powersync`).

## reminders.ts

Такт і налаштування — `components/Reminders.tsx`.

- **Налаштування — стан пристрою**: режими сповіщень і дозвіл у кожного
  пристрою свої.
- **Розклад дає годинник дня, а страву до тексту — план активного профілю.**
  Плану на слот немає — так і кажемо: страву не вигадуємо.
- **Сервера пушів немає.** Сповіщення шле сторінка, поки вона відкрита.
  Пропущене доганяємо лише в межах `CATCH_UP_MINUTES` (фонові таймери сплять).
- **Вимкнення прибирає й показане** (`closeReminders`): сповіщення з тегом
  висить, доки його не закриють. Показані без воркера тримаються в списку —
  реєстрація бачить лише свої.
- Випередження за північ стискається до 00:00 тієї самої доби; тег один на
  слот і добу; позначки надісланого — лише за поточну добу.
- **Відмова в дозволі — не аварія.** `notificationState()` розрізняє
  «браузер не вміє» і «заблоковано»; екран каже це прямо, такт мовчить.
- **Показ — через воркер, коли той керує сторінкою.** Лише так сповіщення
  доживає до згорнутого застосунку, а на Android конструктор `Notification`
  заборонений. `serviceWorker.ready` без контролера не питаємо — обіцянка
  не розв'яжеться. Клік по сповіщенню обробляє воркер
  (`notificationclick` у `public/sw.js`).

## starter-set.ts

Клієнтська частина стартового набору. Формат файлу й правила засіву
для сім'ї — у
[`packages/core/README.md`](../../../../packages/core/README.md#як-засівається),
на сервері — в `infra/README.md`. Тут — пристрій:

- **Автозасів — лише після першої синхронізації.** До неї пул пристрою
  порожній, хоч що лежить на сервері, тож рішення до неї переписало б правки
  сім'ї. Порядок кроків — `autoSeed` (там і тести); сам засів — звичайні
  записи в локальну базу (`seedStarterMeals`), а `claim_starter_set` — після
  них.
- «Засіяно» пристрій кешує в `localStorage` за familyId.
- **Позначка — після запису** (`markSeeded`): збій між ними лишає страви без
  позначки, і наступне відкриття її поставить; навпаки сім'я лишилась би ні з
  чим. `claim` → `false` (позначив інший пристрій) — засіяно однаково. Порядок
  і зупинки на виході з сім'ї — у `starter-set.test.ts`.
- Засіяна сім'я нових страв з оновленого файлу сама не отримує.
- «Додати стартовий набір» рахує відсутні серед живих страв
  (`missingStarterMeals`).

## wake-lock.ts

- **Браузер знімає блокування, щойно сторінку сховали**, тож повернення
  просить його знову.
- Відмова браузера — `onError`, не виняток. API є лише в захищеному
  контексті: на `http://` перемикача немає (`canKeepScreenAwake`).

## pdf-text.ts

- **pdf.js вантажиться лише динамічно** — з обробника події: ~800 КБ із
  воркером не для стартового чанка.
  Воркер — зі збірки (`?url`), не з CDN: інакше офлайн PDF не читається.
- Текст — рядками за `hasEOL`, як його чекає `parsePlanText`; документ у
  воркері закривається (`destroy`) і після скасування — PDF важить мегабайти.
- **`pdfjs-dist` оновлювати, а не відкладати.** Файл приносить користувач із
  пошти. `isEvalSupported: false` із V1 не переїхав: обхід CVE-2024-4367
  старої версії, у 6.x шляху зі `Function` немає.

## Відомі стелі (ponytail)

- **Перший кадр неба — за стандартними вікнами** (`applySky` у `main.tsx`):
  вікна сім'ї — у локальній базі, що відкривається пізніше. Апгрейд — дзеркало вікон у `localStorage` для першого кадру.
- **Стартовий набір кешується до перезавантаження** (`loaded` у
  `starter-set.ts`): набір один на сервер і міняється рідко. Новий файл видно
  після перезавантаження сторінки.
- **Наздоганяння прокрутки — 5 с від монтування** (`catchUpScroll`): локальна
  база відповідає за десятки мілісекунд. Повільніший телефон — підняти
  `timeoutMs`.
- **«Куплено» — на продукт, а не на кількість** (`shopping_check` за
  `item.key`): куплене «На 3 дні» видно купленим і в «Увесь план», де
  кількість більша. Апгрейд — кількість у позначці.
