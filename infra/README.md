# infra — self-host

```bash
git clone https://github.com/<namespace>/meridian && cd meridian
docker compose up
```

Це вся установка. Ні файлів для заповнення, ні ключів для копіювання, ні
портів і адрес для звіряння: секрети стек генерує собі сам, схему накочує сам,
а сервіси знаходять одне одного всередині мережі Compose. Перший запуск —
кілька хвилин (збирається образ застосунку), далі — секунди.

Опис стека й усі рішення — у коментарях [`compose.yaml`](../compose.yaml) в
корені репозиторію; тут те, що в них не поміщається.

| Файл | Призначення |
|------|-------------|
| `../compose.yaml` | Увесь стек: init, db, migrate, auth, rest, powersync, web, caddy |
| `../.env.example` | Необов'язковий: усе має типові значення. Секретів тут немає й не буде |
| `init/generate-secrets.mjs` | Генерує секрети у спільний том при першому запуску |
| `db/roles.sql` | Паролі службових ролей Postgres — раз, під час ініціалізації бази |
| `migrate.Dockerfile` | Одноразовий образ для міграцій `packages/db` |
| `web.Dockerfile` | Прод-образ `apps/web`. Контекст збірки — корінь репозиторію |
| `caddy/Caddyfile` | Єдиний вхід: одне походження, чотири маршрути |
| `powersync/service.yaml` | Конфіг PowerSync Service, монтується лише для читання |
| `powersync/sync-config.yaml` | Правила синхронізації (MER-46): один стрім на сім'ю, сім таблиць |
| `compose.prebuilt.yaml` | Накладка: `web` готовим образом замість збірки |

## Що всередині

Вісім сервісів, з них два одноразові:

| | |
|---|---|
| `init` | генерує секрети й виходить |
| `db` | Postgres із образу Supabase — ролі й схема `auth` уже в ньому |
| `migrate` | накочує міграції `packages/db` і виходить |
| `auth` | GoTrue — реєстрація й вхід |
| `rest` | PostgREST — запис із клієнта (LWW, MER-46) |
| `powersync` | синхронізація на пристрої |
| `web` | сам застосунок (SSR) |
| `caddy` | 80/443; більше назовні не публікується нічого |

Це підмножина офіційного self-host Supabase — рівно ті три сервіси, якими
застосунок користується. Studio, Realtime, Storage, edge-функції, аналітика й
пулер supavisor не піднімаються: звернень до них у коді немає, а кожен — це ще
один контейнер, який має оновлюватись і падати. Версії образів узяті з
офіційного compose Supabase, щоб їх можна було звіряти при оновленні.

Перевірити, що все живе:

```bash
docker compose ps
```

`init` і `migrate` у стані `Exited (0)` — це норма, вони й мають завершитись.

## Свій домен

Одна змінна в `.env` поруч із `compose.yaml`:

```
APP_URL=https://meridian.example.com
```

Схема значуща: `https://` вмикає автоматичний сертифікат Let's Encrypt. Треба
лише, щоб домен резолвився на цей хост (A/AAAA-запис або DDNS), а 80 і 443
доходили ззовні — за NAT це проброс на роутері. Жодних ручних ACME-кроків, і
жодного другого імені хоста: sync живе під тим самим доменом на шляху `/sync`.

⚠️ 80/443 мають бути **вільні на хості**. Вбудована веб-панель керування чи
інший реверс-проксі часто вже їх слухають — тоді Caddy впаде на біндингу порту,
а в GUI-обгортках над Compose це не завжди видно як явну помилку. Або звільнити
порти, або задати `HTTP_PORT`/`HTTPS_PORT` і вказати порт у `APP_URL`.

**Реєстрація відкрита, а пошти в стеку немає.** Тому акаунт підтверджується
автоматично — інакше лист нікуди б не пішов і ввійти було б неможливо. Стек,
доступний з інтернету, це лишає відкритим для будь-кого: завести свої акаунти й
поставити `GOTRUE_DISABLE_SIGNUP=true`, або налаштувати SMTP і вимкнути
`GOTRUE_MAILER_AUTOCONFIRM`.

## Один вхід замість чотирьох портів

Caddy віддає весь стек з одного походження, розкладаючи його шляхами:

| Шлях | Куди |
|------|------|
| `/` | `web` |
| `/auth/v1/*` | `auth` (GoTrue) |
| `/rest/v1/*` | `rest` (PostgREST) |
| `/sync/*` | `powersync` |

Префікси `/auth/v1` і `/rest/v1` — ті самі, що в офіційному Supabase (там їх
роздає kong), тому `supabase-js` працює без налаштувань.

Саме через це в браузері немає ні портів, ні других імен хостів: усе відносно
адреси, яку відкрив користувач. І саме тому `APP_URL` — єдина змінна, якої
взагалі може забракнути: з неї збирається і сайт у Caddy, і адреси для
браузера, і посилання GoTrue.

## Секрети

Пароль Postgres, `JWT_SECRET` і anon-ключ генерує сервіс `init` при першому
запуску й кладе у том `secrets`. У git вони не потрапляють, у `.env` не
потрапляють, у `docker compose config` і в історію команд теж — їх ніхто не
вводить руками.

Подивитись (наприклад, щоб зібрати `apps/web/.env` для розробки):

```bash
docker compose exec -T web sh -c '. /secrets/app.env; echo $ANON_KEY'
```

Файлів два, бо читачі різні: `app.env` читає оболонка сервісів, а PostgREST
оболонки в образі не має взагалі, тож для нього генерується `postgrest.conf`,
який він читає сам.

Генерація **ідемпотентна**: є `app.env` — не чіпаємо. Інакше перезапуск міняв
би пароль під уже наповненою базою й `JWT_SECRET` під уже виданими токенами.
Через це ж `docker compose down -v` — не «перезапуск», а видалення стека: разом
із томами зникають і секрети, і база.

## Готовий образ

Збірка `web` — найдовший крок першого запуску. Якщо образ уже опубліковано
(`.github/workflows/docker-publish.yml`, MER-58), його можна підставити
замість збірки:

```
WEB_IMAGE=<namespace>/meridian:staging
```

```bash
docker compose -f compose.yaml -f infra/compose.prebuilt.yaml up -d
```

`<namespace>` — власник образу в реєстрі, тобто обліковий запис із секрету
`DOCKERHUB_USERNAME`. У репозиторії конкретне ім'я ніде не зашите.

Репозиторій при цьому все одно потрібен: конфіги (`caddy/`, `powersync/`,
`init/`, `db/`) сервіси монтують із нього, а `migrate` збирається з
`packages/db`. Накладка економить збірку застосунку, не клонування.

### Теги

| Тег | Звідки береться |
|-----|-----------------|
| `latest` | пуш у гілку за замовчуванням (`main`) і git-тег `vX.Y.Z` |
| `staging` | пуш у `staging` — поки V2 живе саме там, це найсвіжіший образ |
| `sha-<короткий-sha>` | кожен пуш — щоб відкотитись на конкретний коміт |
| `X.Y.Z` | git-тег `vX.Y.Z` |

### Що всередині образу

Рантайм-шар — це `node:22-alpine`, з якого прибрано npm, corepack і yarn, плюс
вивід nitro. Більше нічого: єдина команда образу — `node
.output/server/index.mjs`, а вивід самодостатній, тож менеджер пакетів там не
запускається ніколи (MER-60). Без цієї чистки в публічний образ їхав повний
npm CLI — ~185 пакетів, які ніхто не виконує, зате з усіма їхніми CVE (на
2026-08-10 базовий образ давав 1 Critical + 7 High + 8 Medium). Після чистки
`docker scout cves` показує **0** при 26 пакетах у SBOM.

Щоб це не повернулося тихо з наступним оновленням бази, `docker-publish.yml`
після збірки сканує образ (`docker/scout-action`) і падає на будь-якій
Critical чи High.

### Секрети репозиторію

Workflow нічого не публікує, доки в налаштуваннях репозиторію
(Settings → Secrets and variables → Actions) не з'являться два секрети:

| Секрет | Значення |
|--------|----------|
| `DOCKERHUB_USERNAME` | ім'я користувача Docker Hub — воно ж namespace, у який публікується образ |
| `DOCKERHUB_TOKEN` | **access token** Docker Hub із правом `Read & Write`, не пароль акаунта |

Токен, а не пароль: його видно в списку, можна відкликати окремо й він не
відмикає сам акаунт. Без секретів крок логіну падає — образ не публікується,
але код у репозиторії від цього не страждає.

## Розробка застосунку

Стек — це прод-збірка. Для роботи над інтерфейсом зручніше `pnpm dev` поруч із
уже піднятим стеком: він бере ту саму базу, той самий GoTrue і той самий sync,
але з гарячою заміною модулів.

```bash
docker compose up -d
docker compose exec -T web sh -c '. /secrets/app.env; printf "PUBLIC_SUPABASE_URL=%s\nPUBLIC_SUPABASE_ANON_KEY=%s\nPUBLIC_POWERSYNC_URL=%s/sync\n" "$PUBLIC_SUPABASE_URL" "$ANON_KEY" "$PUBLIC_SUPABASE_URL"' > apps/web/.env
pnpm install && pnpm dev
```

Другий рядок потрібен тому, що `pnpm dev` — це Vite поза стеком: змінні він
підставляє на етапі збірки, а anon-ключ існує лише всередині стека.

Міграції під час розробки — тим самим одноразовим сервісом, не з хоста:

```bash
docker compose up migrate
```

Порт Postgres назовні не публікується свідомо: до бази ходять лише сервіси
стека. Для разових запитів є `docker compose exec db psql -U postgres`.

## Рішення, які тут прийняті

**Секрети генеруються, а не запитуються.** Головна вимога до self-host —
`docker compose up` і нічого більше. Compose підставляє змінні, коли ЧИТАЄ
файл, тобто до старту будь-якого контейнера, — а отже згенерувати секрет і
одразу підставити його в той самий запуск неможливо. Тому сервіси, яким
потрібен секрет, стартують через тонку оболонку: вона читає `/secrets/app.env`
і через `exec` віддає керування рідній команді образу. `exec` обов'язковий —
інакше PID 1 лишається за `sh` і сигнал зупинки не доходить до сервісу.

> **Наслідок.** У образі PostgREST немає навіть `/bin/sh`, тож для нього
> оболонка неможлива — він єдиний отримує згенерований конфіг-файл і читає його
> сам. Файли в томі мають права 0644, а не 0600: GoTrue, PostgREST і PowerSync
> працюють не від root (uid `supabase`, 1000 і 901), і 0600 від root вони б не
> прочитали.

**Постачальник даних — не весь Supabase, а три його сервіси.** Офіційний
self-host — це ~11 контейнерів; застосунок звертається до трьох (GoTrue,
PostgREST, Postgres). Решта — Studio, Realtime, Storage, edge-функції,
аналітика з vector, пулер supavisor — у коді не згадується жодного разу.
Разом з ними пішли й дві найдорожчі пастки старої установки: орендар supavisor
у рядках підключення й накладка, яку Compose мовчки ігнорує, якщо не дописати
її в `COMPOSE_FILE`.

> Схема це витримує, бо вона ніколи й не залежала від Supabase: RLS читає GUC
> `request.jwt.claims` напряму, а не через `auth.jwt()`, і гранти
> `supabase_auth_admin` стоять під `IF EXISTS` (MER-44/45). Ролі `anon`,
> `authenticated`, `service_role`, `authenticator`, `supabase_auth_admin`
> приходять з образу `supabase/postgres` — `db/roles.sql` лише видає паролі
> двом, які реально входять у базу по мережі.

**Хук доступу — рядок у `compose.yaml`, а не окремий крок установки.** Без
`GOTRUE_HOOK_CUSTOM_ACCESS_TOKEN_*` GoTrue не покличе
`public.custom_access_token_hook`, у токені не буде claim `family_id`, і
застосунок не побачить жодного рядка — мовчки, без помилки (MER-45). Раніше це
був крок, який найлегше було пропустити; тепер його неможливо не зробити.

**Схему накочує стек, а не людина.** `migrate` — одноразовий сервіс, і все, що
працює з даними, чекає на його успішне завершення (`service_completed_successfully`).
Тому застосунок не може стартувати на базі без таблиць, RLS і хука.

**Сховище бакетів — Postgres, не MongoDB.** Демо PowerSync використовує MongoDB,
але це +2 сервіси (сам Mongo і ініціалізація реплікасету) й окремий рушій БД.
Postgres як bucket storage підтримується офіційно з 1.3.8; PowerSync створює
власну схему в указаній базі сам.

> **Наслідок для схеми (зроблено в MER-44).** Сховище живе в тій самій базі,
> яку PowerSync реплікує, тому публікація `powersync` перелічує таблиці явно —
> `CREATE PUBLICATION powersync FOR TABLE ...` у міграції
> `packages/db/drizzle/0002_replication.sql`. Варіант `FOR ALL TABLES` затягнув
> би в реплікацію власні таблиці PowerSync і зациклив сервіс. Нову таблицю
> треба додавати в публікацію руками — інакше вона не поїде на пристрої.
> Так і зроблено в MER-55: `0003_prefs_shopping.sql` доповнює публікацію
> через `ALTER PUBLICATION powersync ADD TABLE`.

**Реплікація йде прямо в `db`.** Логічна реплікація потребує прямого з'єднання,
пулер її ламає — колись це означало «не через supavisor», тепер пулера в стеку
немає взагалі, і `PS_DATABASE_URI` дивиться на `db:5432`.

**Користувач реплікації — поки що `postgres`.** Так робить офіційне демо
PowerSync. Виділену роль `powersync_role` (`LOGIN REPLICATION BYPASSRLS` +
`SELECT` на таблицях схеми) уже заводить міграція MER-44, але **без пароля** —
секрети в git не потрапляють, а без пароля роль не може ввійти.

**PowerSync перевіряє токени спільним секретом, а не JWKS** (MER-46). GoTrue у
self-host досі підписує токени симетричним ключем: у них немає `kid`, а
`/.well-known/jwks.json` віддає `{"keys":[]}`. Тому в `service.yaml` поруч із
`jwks_uri` стоїть `supabase_jwt_secret`. Без нього sync відповідає
`401 PSYNC_S2101` («no key matched the token KID»), і виглядає це як «правила
не працюють», хоч і правила, і claim правильні. Обидва способи лишаються поруч
навмисно: після переходу на асиметричні ключі JWKS наповниться й почне вигравати
сам.

**`web` не знає про сесію користувача — і не має знати.** Вхід робить браузер,
сесія живе на пристрої. Від сервера потрібен лише публічний конфіг
(`PUBLIC_*`), який він віддає під час SSR; інакше застосунок перестав би бути
local-first.

## Перевірка на живому стеку

Що саме має бути видно, коли все справді працює:

```bash
# у токені є family_id — інакше RLS не покаже жодного рядка (MER-45)
docker compose logs auth | grep -i error

# бакет сім'ї зійшовся — claim доїхав і правила його прочитали (MER-46)
docker compose logs powersync | grep "New checkpoint"
```

У логах PowerSync після входу має з'явитися бакет
`family_data|0["<family_id>"]`. Порожньо й без помилок — див. абзац про хук
доступу вище.

## Розбіжності з інструкцією V2

Інструкція вимагає звіряти кожне ім'я з офіційною документацією і фіксувати
розбіжності. Знайдено чотири:

| В інструкції | Насправді | Джерело |
|--------------|-----------|---------|
| конфіг називається `powersync.yaml` | `service.yaml` (+ окремий `sync-config.yaml`), шлях задається `POWERSYNC_CONFIG_PATH` | `powersync-ja/self-host-demo` |
| `client_auth.allow_local_jwks` вмикає локальні JWKS-адреси | такого ключа більше немає; є зворотний `block_local_jwks` (типово `false`) | JSON-схема `@powersync/service-schema` |
| «bucket по `family_id`» | бакети — це legacy `bucket_definitions`; актуальні Sync Streams з `config: edition: 3`, параметр читається `auth.parameter('family_id')` | docs.powersync.com/sync/streams |
| для перевірки токенів досить `PS_JWKS_URL` | self-host GoTrue лишається на HS256, JWKS порожній — потрібен ще `client_auth.supabase_jwt_secret` | розділ вище, перевірено на живому стеку |

Імена змінних середовища з контракту (`PS_DATABASE_URI`, `PS_JWKS_URL`,
`POWERSYNC_URL`, `PUBLIC_*`) збережено як є: у конфізі PowerSync вони
підставляються через `!env`, а той приймає будь-яке ім'я з префіксом `PS_`.
