# infra — self-host

```bash
git clone https://github.com/<namespace>/meridian && cd meridian
docker compose up
```

Це вся установка. Ні файлів для заповнення, ні ключів для копіювання, ні
портів і адрес для звіряння: секрети стек генерує собі сам, схему накочує сам,
а сервіси знаходять одне одного всередині мережі Compose. Перший запуск —
кілька хвилин (збирається образ застосунку), далі — секунди.

Інструкція для людини, яка піднімає власний сервер. Рішення, правила й карта
файлів для тих, хто змінює стек, — у [`DECISIONS.md`](DECISIONS.md).

---

## Що всередині

Сім сервісів, з них два одноразові:

| | |
|---|---|
| `init` | генерує секрети й виходить |
| `db` | Postgres із образу Supabase — ролі й схема `auth` уже в ньому |
| `migrate` | накочує міграції `packages/db` і виходить |
| `auth` | GoTrue — реєстрація й вхід |
| `rest` | PostgREST — запис із клієнта (LWW, MER-46) |
| `powersync` | синхронізація на пристрої |
| `caddy` | 80/443 і сам застосунок — статичні файли в образі; більше назовні не публікується нічого |

Це підмножина офіційного self-host Supabase — рівно ті три сервіси, якими
застосунок користується. Studio, Realtime, Storage, edge-функції, аналітика й
пулер supavisor не піднімаються: звернень до них у коді немає, а кожен — це ще
один контейнер, який має оновлюватись і падати. Версії образів узяті з
офіційного compose Supabase, щоб їх можна було звіряти при оновленні.

Перевірити, що все живе:

```bash
docker compose ps
```

`init` і `migrate` у стані `Exited (0)` — це норма, вони й мають завершитись.

## Свій домен

Одна змінна в `.env` поруч із `compose.yaml`:

```
APP_URL=https://meridian.example.com
```

Схема значуща: `https://` вмикає автоматичний сертифікат Let's Encrypt. Треба
лише, щоб домен резолвився на цей хост (A/AAAA-запис або DDNS), а 80 і 443
доходили ззовні — за NAT це проброс на роутері. Жодних ручних ACME-кроків, і
жодного другого імені хоста: sync живе під тим самим доменом на шляху `/sync`.

⚠️ 80/443 мають бути **вільні на хості**. Вбудована веб-панель керування чи
інший реверс-проксі часто вже їх слухають — тоді Caddy впаде на біндингу порту,
а в GUI-обгортках над Compose це не завжди видно як явну помилку. Або звільнити
порти, або задати `HTTP_PORT`/`HTTPS_PORT` і вказати порт у `APP_URL`.

**Порт у `APP_URL` має збігатися з `HTTP_PORT` або `HTTPS_PORT`** (MER-74).
Caddy слухає саме той порт, що в адресі сайту, а compose публікує його один в
один: `HTTPS_PORT=8443` + `APP_URL=https://meridian.example.com:8443`. Без порту
в адресі Caddy слухає `HTTP_PORT`/`HTTPS_PORT` усередині контейнера, тож за
NAT досить пробросити зовнішні 80/443 на них — і Let's Encrypt працює далі.

### Домашній сервер без домену

`http://<IP>` для застосунку не годиться: браузер вважає захищеним контекстом
лише HTTPS і `localhost`, а без нього PowerSync не відкриває локальну базу
(`navigator.locks` недоступний) — екрани кажуть про це прямо (MER-73). Тож і в
локальній мережі — `https://`:

```
APP_URL=https://192.168.1.10:8443
HTTPS_PORT=8443
HTTP_PORT=8080
```

Відкривати одразу `https://…:8443`: автоматичний редирект Caddy з HTTP веде на
`https://<IP>/` без порту — він розрахований на зовнішній 443, тож у локальній
мережі на нього не покладатися.

Для IP-адреси Let's Encrypt сертифікат не видає, і Caddy підписує його сам —
своїм локальним центром сертифікації. Перший раз браузер попередить про
невідомий центр. Щоб попередження зникло, а офлайн і встановлення PWA
запрацювали (service worker на сертифікаті з помилкою не реєструється),
кореневий сертифікат цього центру треба додати в довірені на кожному пристрої:

```sh
docker compose cp caddy:/data/caddy/pki/authorities/local/root.crt ./meridian-local-ca.crt
```

Файл лежить у томі `caddy-data` і переживає перезапуски; новий з'явиться лише
разом із новим томом.

### Закрити реєстрацію — крок установки, а не порада

Реєстрація типово відкрита, і типове значення лишається таким свідомо: інакше
свіжий `docker compose up` не дав би завести навіть перший акаунт. Але для
стека, який видно з інтернету, «відкрита» означає «зареєструватись може
будь-хто». Тому вихід у публічний доступ не завершено, доки не зроблено це:

1. Підняти стек зі своїм `APP_URL` — `docker compose up -d`.
2. Відкрити сайт і завести **всі** потрібні акаунти: по одному на людину. В
   одну сім'ю вони сходяться потім, кодом запрошення з екрана «Сім'я».
3. Дописати в `.env` поруч із `compose.yaml`:

   ```
   GOTRUE_DISABLE_SIGNUP=true
   ```

4. Перепідняти лише GoTrue — решти стека це не стосується:

   ```bash
   docker compose up -d auth
   ```

5. Переконатися, що справді закрито (ключа тут не треба — GoTrue не перевіряє
   `apikey`, це робить kong, якого в стеку немає):

   ```bash
   curl -s -X POST https://meridian.example.com/auth/v1/signup \
     -H 'Content-Type: application/json' \
     -d '{"email":"probe@example.com","password":"probe-password"}'
   ```

   `{"code":422,"error_code":"signup_disabled",...}` — закрито. `200` і токен у
   відповіді — ще відкрито, крок не спрацював (і щойно з'явився зайвий акаунт).
   Вхід наявних акаунтів лишається робочим, а форма реєстрації в застосунку
   відповідає «Реєстрацію на цьому сервері вимкнено».

### Що закрита реєстрація ламає

Дві речі, і чесніше знати про них заздалегідь, ніж наштовхнутись потім. Обидві
випливають з однієї причини — пошти в стеку немає, — і жодну закрита реєстрація
не лікує.

**Нову людину в сім'ю просто так не додати.** `accept_family_invite` бере акаунт
із токена (MER-45), тобто той, кого запрошують, має вже мати акаунт, а при
закритій реєстрації завести його нема як. Порядок такий:

1. `GOTRUE_DISABLE_SIGNUP=false` в `.env` + `docker compose up -d auth`;
2. новачок реєструється на сайті;
3. член сім'ї створює код на екрані «Сім'я», новачок вводить його;
4. `GOTRUE_DISABLE_SIGNUP=true` + `docker compose up -d auth`.

Поки вікно відкрите, зареєструватись може будь-хто, хто в цю мить знає адресу, —
тож тримати його коротким. Обійти вікно нема чим: адмін-запрошення GoTrue
(`POST /auth/v1/invite`) вимагає `service_role`-ключа, а стек його не генерує
взагалі — у `/secrets/app.env` лежить тільки anon.

**Відновлення пароля не працює — ні при закритій реєстрації, ні при відкритій.**
GoTrue пише в лог `Noop mail client being used`, `POST /auth/v1/recover`
відповідає `200 {}`, і лист не йде нікуди. Тому в застосунку немає й посилання
«забув пароль»: воно обіцяло б лист, якого не буде. Забутий пароль зараз
міняють руками в базі (`docker compose exec db psql -U postgres`, таблиця
`auth.users`) — або налаштовують SMTP і вимикають `GOTRUE_MAILER_AUTOCONFIRM`,
після чого починають працювати і підтвердження пошти, і відновлення.

## Стартовий набір страв

Необов'язковий крок (MER-77). Стартовий набір — страви з планів дієтолога, якими
засівається пул кожної сім'ї на цьому сервері при першому відкритті. Без нього
все працює як раніше: пул порожній, страви додають руками чи з PDF.

1. Покласти JSON-файл набору на сервер **поза репозиторієм** — плани
   персональні, а репозиторій публічний (`.gitignore` про всяк випадок
   ігнорує `starter-set*.json`). Формат —
   [`packages/core/README.md`](../packages/core/README.md#стартовий-набір-формат-файлу-mer-77),
   приклад із вигаданими стравами — [`starter-set.example.json`](starter-set.example.json).
2. Перевірити: `pnpm starter:check /srv/meridian/starter-set.json` (потрібні
   Node 22+ і `pnpm install`; без них помилки формату покаже застосунок на
   «Стравах»).
3. Вказати шлях у `.env` поруч із `compose.yaml` і перезапустити `migrate`:

   ```
   STARTER_SET_FILE=/srv/meridian/starter-set.json
   ```

   ```bash
   docker compose up migrate
   ```

   У журналі — `стартовий набір завантажено`. Набору немає: `STARTER_SET_FILE`
   порожня.

Як це влаштовано:

- **Файл монтується лише в `migrate`** (усередині — `/starter/starter-set.json`),
  а той кладе вміст у таблицю `starter.starter_set`. Схема `starter` поза
  PostgREST, тож набір віддають тільки три RPC (`0007_starter_set.sql`), і лише
  автентифікованому члену сім'ї. Через Caddy набір публічно не видно ніяк.
- **Хибний шлях зупиняє запуск** (`create_host_path: false`), а не тихо
  створює порожній каталог. Зіпсований JSON стек НЕ зупиняє: у журналі
  попередження, у базі лишається попередній набір.
- **Прибрати набір** — очистити `STARTER_SET_FILE` і `docker compose up
  migrate`. Уже засіяні страви лишаються в пулах сімей.
- **Автозасів — один раз на сім'ю й лише в порожній пул**, повтор і другий
  пристрій страв не дублюють (виведені id). Сім'я, у якої страви вже є,
  автозасіву не отримує — лише кнопку «Додати стартовий набір» на «Стравах».
  Оновлений файл наявних страв у пулі не переписує, а нові страви з нього
  засіяна сім'я отримає тією самою кнопкою: вона з'являється, щойно в наборі
  є страви, яких у пулі немає. Новий файл застосунок бачить після
  перезавантаження сторінки.

## Секрети

Пароль Postgres, `JWT_SECRET` і anon-ключ генерує сервіс `init` при першому
запуску й кладе у том `secrets`. У git вони не потрапляють, у `.env` не
потрапляють, у `docker compose config` і в історію команд теж — їх ніхто не
вводить руками.

Подивитись (наприклад, щоб зібрати `apps/web/.env` для розробки):

```bash
docker compose exec -T caddy sh -c '. /secrets/app.env; echo $ANON_KEY'
```

Файлів два, бо читачі різні: `app.env` читає оболонка сервісів, а PostgREST
оболонки в образі не має взагалі, тож для нього генерується `postgrest.conf`,
який він читає сам.

Генерація **ідемпотентна**: є `app.env` — не чіпаємо. Інакше перезапуск міняв
би пароль під уже наповненою базою й `JWT_SECRET` під уже виданими токенами.
Через це ж `docker compose down -v` — не «перезапуск», а видалення стека: разом
із томами зникають і секрети, і база.

## Готовий образ

Збірка образу застосунку — найдовший крок першого запуску. Якщо образ уже опубліковано
(`.github/workflows/docker-publish.yml`, MER-58), його можна підставити
замість збірки:

```
WEB_IMAGE=<namespace>/meridian:staging
```

```bash
docker compose -f compose.yaml -f infra/compose.prebuilt.yaml up -d
```

`<namespace>` — власник образу в реєстрі, тобто обліковий запис із секрету
`DOCKERHUB_USERNAME`. У репозиторії конкретне ім'я ніде не зашите.

Репозиторій при цьому все одно потрібен: конфіги (`caddy/`, `powersync/`,
`init/`, `db/`) сервіси монтують із нього, а `migrate` монтує з нього ж
`packages/db`. Накладка економить збірку застосунку, не клонування.

### Теги

| Тег | Звідки береться |
|-----|-----------------|
| `latest` | пуш у гілку за замовчуванням (`main`) і git-тег `vX.Y.Z` |
| `staging` | пуш у `staging` — поки V2 живе саме там, це найсвіжіший образ |
| `sha-<короткий-sha>` | кожен пуш — щоб відкотитись на конкретний коміт |
| `X.Y.Z` | git-тег `vX.Y.Z` |

### Секрети репозиторію

Workflow нічого не публікує, доки в налаштуваннях репозиторію
(Settings → Secrets and variables → Actions) не з'являться два секрети:

| Секрет | Значення |
|--------|----------|
| `DOCKERHUB_USERNAME` | ім'я користувача Docker Hub — воно ж namespace, у який публікується образ |
| `DOCKERHUB_TOKEN` | **access token** Docker Hub із правом `Read & Write`, не пароль акаунта |

Токен, а не пароль: його видно в списку, можна відкликати окремо й він не
відмикає сам акаунт. Без секретів крок логіну падає — образ не публікується,
але код у репозиторії від цього не страждає.

## Розробка застосунку

Стек — це прод-збірка. Для роботи над інтерфейсом зручніше `pnpm dev` поруч із
уже піднятим стеком: він бере ту саму базу, той самий GoTrue і той самий sync,
але з гарячою заміною модулів.

```bash
docker compose up -d
docker compose exec -T caddy sh -c '. /secrets/app.env; printf "PUBLIC_SUPABASE_URL=%s\nPUBLIC_SUPABASE_ANON_KEY=%s\nPUBLIC_POWERSYNC_URL=%s/sync\n" "$PUBLIC_SUPABASE_URL" "$ANON_KEY" "$PUBLIC_SUPABASE_URL"' > apps/web/.env
pnpm install && pnpm dev
```

Другий рядок потрібен тому, що `pnpm dev` — це Vite поза стеком: змінні він
підставляє на етапі збірки, а anon-ключ існує лише всередині стека.

Міграції під час розробки — тим самим одноразовим сервісом, не з хоста:

```bash
docker compose up migrate
```

Порт Postgres назовні не публікується свідомо: до бази ходять лише сервіси
стека. Для разових запитів є `docker compose exec db psql -U postgres`.
