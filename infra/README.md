# infra — self-host

```bash
git clone https://github.com/<namespace>/meridian && cd meridian
docker compose up
```

Це вся установка. Ні файлів для заповнення, ні ключів для копіювання, ні
портів і адрес для звіряння: секрети стек генерує собі сам, схему накочує сам,
а сервіси знаходять одне одного всередині мережі Compose. Перший запуск —
кілька хвилин (збирається образ застосунку), далі — секунди.

Опис стека й усі рішення — у коментарях [`compose.yaml`](../compose.yaml) в
корені репозиторію; тут те, що в них не поміщається.

| Файл | Призначення |
|------|-------------|
| `../compose.yaml` | Увесь стек: init, db, migrate, auth, rest, powersync, caddy |
| `../.env.example` | Необов'язковий: усе має типові значення. Секретів тут немає й не буде |
| `init/generate-secrets.mjs` | Генерує секрети у спільний том при першому запуску |
| `db/roles.sql` | Паролі службових ролей Postgres — раз, під час ініціалізації бази |
| `web.Dockerfile` | Образ `caddy`: Caddy зі статичною збіркою `apps/web`. Контекст збірки — корінь репозиторію |
| `caddy/Caddyfile` | Єдиний вхід: одне походження, чотири маршрути, конфіг застосунку в `index.html` |
| `powersync/service.yaml` | Конфіг PowerSync Service, монтується лише для читання |
| `powersync/sync-config.yaml` | Правила синхронізації (MER-46): один стрім на сім'ю, сім таблиць |
| `compose.prebuilt.yaml` | Накладка: `caddy` готовим образом замість збірки |
| `starter-set.example.json` | Вигаданий приклад стартового набору страв (MER-77) — формат і перевірка, не дані |

## Що всередині

Сім сервісів, з них два одноразові:

| | |
|---|---|
| `init` | генерує секрети й виходить |
| `db` | Postgres із образу Supabase — ролі й схема `auth` уже в ньому |
| `migrate` | накочує міграції `packages/db` і виходить |
| `auth` | GoTrue — реєстрація й вхід |
| `rest` | PostgREST — запис із клієнта (LWW, MER-46) |
| `powersync` | синхронізація на пристрої |
| `caddy` | 80/443 і сам застосунок — статичні файли в образі; більше назовні не публікується нічого |

Це підмножина офіційного self-host Supabase — рівно ті три сервіси, якими
застосунок користується. Studio, Realtime, Storage, edge-функції, аналітика й
пулер supavisor не піднімаються: звернень до них у коді немає, а кожен — це ще
один контейнер, який має оновлюватись і падати. Версії образів узяті з
офіційного compose Supabase, щоб їх можна було звіряти при оновленні.

Перевірити, що все живе:

```bash
docker compose ps
```

`init` і `migrate` у стані `Exited (0)` — це норма, вони й мають завершитись.

## Свій домен

Одна змінна в `.env` поруч із `compose.yaml`:

```
APP_URL=https://meridian.example.com
```

Схема значуща: `https://` вмикає автоматичний сертифікат Let's Encrypt. Треба
лише, щоб домен резолвився на цей хост (A/AAAA-запис або DDNS), а 80 і 443
доходили ззовні — за NAT це проброс на роутері. Жодних ручних ACME-кроків, і
жодного другого імені хоста: sync живе під тим самим доменом на шляху `/sync`.

⚠️ 80/443 мають бути **вільні на хості**. Вбудована веб-панель керування чи
інший реверс-проксі часто вже їх слухають — тоді Caddy впаде на біндингу порту,
а в GUI-обгортках над Compose це не завжди видно як явну помилку. Або звільнити
порти, або задати `HTTP_PORT`/`HTTPS_PORT` і вказати порт у `APP_URL`.

**Порт у `APP_URL` має збігатися з `HTTP_PORT` або `HTTPS_PORT`** (MER-74).
Caddy слухає саме той порт, що в адресі сайту, а compose публікує його один в
один: `HTTPS_PORT=8443` + `APP_URL=https://meridian.example.com:8443`. Без порту
в адресі Caddy слухає `HTTP_PORT`/`HTTPS_PORT` усередині контейнера, тож за
NAT досить пробросити зовнішні 80/443 на них — і Let's Encrypt працює далі.

### Домашній сервер без домену

`http://<IP>` для застосунку не годиться: браузер вважає захищеним контекстом
лише HTTPS і `localhost`, а без нього PowerSync не відкриває локальну базу
(`navigator.locks` недоступний) — екрани кажуть про це прямо (MER-73). Тож і в
локальній мережі — `https://`:

```
APP_URL=https://192.168.1.10:8443
HTTPS_PORT=8443
HTTP_PORT=8080
```

Відкривати одразу `https://…:8443`: автоматичний редирект Caddy з HTTP веде на
`https://<IP>/` без порту — він розрахований на зовнішній 443, тож у локальній
мережі на нього не покладатися.

Для IP-адреси Let's Encrypt сертифікат не видає, і Caddy підписує його сам —
своїм локальним центром сертифікації. Перший раз браузер попередить про
невідомий центр. Щоб попередження зникло, а офлайн і встановлення PWA
запрацювали (service worker на сертифікаті з помилкою не реєструється),
кореневий сертифікат цього центру треба додати в довірені на кожному пристрої:

```sh
docker compose cp caddy:/data/caddy/pki/authorities/local/root.crt ./meridian-local-ca.crt
```

Файл лежить у томі `caddy-data` і переживає перезапуски; новий з'явиться лише
разом із новим томом.

### Закрити реєстрацію — крок установки, а не порада

Реєстрація типово відкрита, і типове значення лишається таким свідомо: інакше
свіжий `docker compose up` не дав би завести навіть перший акаунт. Але для
стека, який видно з інтернету, «відкрита» означає «зареєструватись може
будь-хто». Тому вихід у публічний доступ не завершено, доки не зроблено це:

1. Підняти стек зі своїм `APP_URL` — `docker compose up -d`.
2. Відкрити сайт і завести **всі** потрібні акаунти: по одному на людину. В
   одну сім'ю вони сходяться потім, кодом запрошення з екрана «Сім'я».
3. Дописати в `.env` поруч із `compose.yaml`:

   ```
   GOTRUE_DISABLE_SIGNUP=true
   ```

4. Перепідняти лише GoTrue — решти стека це не стосується:

   ```bash
   docker compose up -d auth
   ```

5. Переконатися, що справді закрито (ключа тут не треба — GoTrue не перевіряє
   `apikey`, це робить kong, якого в стеку немає):

   ```bash
   curl -s -X POST https://meridian.example.com/auth/v1/signup \
     -H 'Content-Type: application/json' \
     -d '{"email":"probe@example.com","password":"probe-password"}'
   ```

   `{"code":422,"error_code":"signup_disabled",...}` — закрито. `200` і токен у
   відповіді — ще відкрито, крок не спрацював (і щойно з'явився зайвий акаунт).
   Вхід наявних акаунтів лишається робочим, а форма реєстрації в застосунку
   відповідає «Реєстрацію на цьому сервері вимкнено».

### Що закрита реєстрація ламає

Дві речі, і чесніше знати про них заздалегідь, ніж наштовхнутись потім. Обидві
випливають з однієї причини — пошти в стеку немає, — і жодну закрита реєстрація
не лікує.

**Нову людину в сім'ю просто так не додати.** `accept_family_invite` бере акаунт
із токена (MER-45), тобто той, кого запрошують, має вже мати акаунт, а при
закритій реєстрації завести його нема як. Порядок такий:

1. `GOTRUE_DISABLE_SIGNUP=false` в `.env` + `docker compose up -d auth`;
2. новачок реєструється на сайті;
3. член сім'ї створює код на екрані «Сім'я», новачок вводить його;
4. `GOTRUE_DISABLE_SIGNUP=true` + `docker compose up -d auth`.

Поки вікно відкрите, зареєструватись може будь-хто, хто в цю мить знає адресу, —
тож тримати його коротким. Обійти вікно нема чим: адмін-запрошення GoTrue
(`POST /auth/v1/invite`) вимагає `service_role`-ключа, а стек його не генерує
взагалі — у `/secrets/app.env` лежить тільки anon.

**Відновлення пароля не працює — ні при закритій реєстрації, ні при відкритій.**
GoTrue пише в лог `Noop mail client being used`, `POST /auth/v1/recover`
відповідає `200 {}`, і лист не йде нікуди. Тому в застосунку немає й посилання
«забув пароль»: воно обіцяло б лист, якого не буде. Забутий пароль зараз
міняють руками в базі (`docker compose exec db psql -U postgres`, таблиця
`auth.users`) — або налаштовують SMTP і вимикають `GOTRUE_MAILER_AUTOCONFIRM`,
після чого починають працювати і підтвердження пошти, і відновлення.

## Стартовий набір страв

Необов'язковий крок (MER-77). Стартовий набір — страви з планів дієтолога, якими
засівається пул кожної сім'ї на цьому сервері при першому відкритті. Без нього
все працює як раніше: пул порожній, страви додають руками чи з PDF.

1. Покласти JSON-файл набору на сервер **поза репозиторієм** — плани
   персональні, а репозиторій публічний (`.gitignore` про всяк випадок
   ігнорує `starter-set*.json`). Формат —
   [`packages/core/README.md`](../packages/core/README.md#стартовий-набір-формат-файлу-mer-77),
   приклад із вигаданими стравами — [`starter-set.example.json`](starter-set.example.json).
2. Перевірити: `pnpm starter:check /srv/meridian/starter-set.json` (потрібні
   Node 22+ і `pnpm install`; без них помилки формату покаже застосунок на
   «Стравах»).
3. Вказати шлях у `.env` поруч із `compose.yaml` і перезапустити `migrate`:

   ```
   STARTER_SET_FILE=/srv/meridian/starter-set.json
   ```

   ```bash
   docker compose up migrate
   ```

   У журналі — `стартовий набір завантажено`. Набору немає: `STARTER_SET_FILE`
   порожня.

Як це влаштовано:

- **Файл монтується лише в `migrate`** (усередині — `/starter/starter-set.json`),
  а той кладе вміст у таблицю `starter.starter_set`. Схема `starter` поза
  PostgREST, тож набір віддають тільки три RPC (`0007_starter_set.sql`), і лише
  автентифікованому члену сім'ї. Через Caddy набір публічно не видно ніяк.
- **Хибний шлях зупиняє запуск** (`create_host_path: false`), а не тихо
  створює порожній каталог. Зіпсований JSON стек НЕ зупиняє: у журналі
  попередження, у базі лишається попередній набір.
- **Прибрати набір** — очистити `STARTER_SET_FILE` і `docker compose up
  migrate`. Уже засіяні страви лишаються в пулах сімей.
- **Автозасів — один раз на сім'ю й лише в порожній пул**, повтор і другий
  пристрій страв не дублюють (виведені id). Сім'я, у якої страви вже є,
  автозасіву не отримує — лише кнопку «Додати стартовий набір» на «Стравах».
  Оновлений файл наявних страв у пулі не переписує, а нові страви з нього
  засіяна сім'я отримає тією самою кнопкою: вона з'являється, щойно в наборі
  є страви, яких у пулі немає. Новий файл застосунок бачить після
  перезавантаження сторінки.

## Один вхід замість чотирьох портів

Caddy віддає весь стек з одного походження, розкладаючи його шляхами:

| Шлях | Куди |
|------|------|
| `/` | застосунок — статичні файли з образу `caddy` |
| `/auth/v1/*` | `auth` (GoTrue) |
| `/rest/v1/*` | `rest` (PostgREST) |
| `/sync/*` | `powersync` |

Префікси `/auth/v1` і `/rest/v1` — ті самі, що в офіційному Supabase (там їх
роздає kong), тому `supabase-js` працює без налаштувань.

Саме через це в браузері немає ні портів, ні других імен хостів: усе відносно
адреси, яку відкрив користувач. І саме тому `APP_URL` — єдина змінна, якої
взагалі може забракнути: з неї збирається і сайт у Caddy, і адреси для
браузера, і посилання GoTrue.

## Секрети

Пароль Postgres, `JWT_SECRET` і anon-ключ генерує сервіс `init` при першому
запуску й кладе у том `secrets`. У git вони не потрапляють, у `.env` не
потрапляють, у `docker compose config` і в історію команд теж — їх ніхто не
вводить руками.

Подивитись (наприклад, щоб зібрати `apps/web/.env` для розробки):

```bash
docker compose exec -T caddy sh -c '. /secrets/app.env; echo $ANON_KEY'
```

Файлів два, бо читачі різні: `app.env` читає оболонка сервісів, а PostgREST
оболонки в образі не має взагалі, тож для нього генерується `postgrest.conf`,
який він читає сам.

Генерація **ідемпотентна**: є `app.env` — не чіпаємо. Інакше перезапуск міняв
би пароль під уже наповненою базою й `JWT_SECRET` під уже виданими токенами.
Через це ж `docker compose down -v` — не «перезапуск», а видалення стека: разом
із томами зникають і секрети, і база.

## Готовий образ

Збірка образу застосунку — найдовший крок першого запуску. Якщо образ уже опубліковано
(`.github/workflows/docker-publish.yml`, MER-58), його можна підставити
замість збірки:

```
WEB_IMAGE=<namespace>/meridian:staging
```

```bash
docker compose -f compose.yaml -f infra/compose.prebuilt.yaml up -d
```

`<namespace>` — власник образу в реєстрі, тобто обліковий запис із секрету
`DOCKERHUB_USERNAME`. У репозиторії конкретне ім'я ніде не зашите.

Репозиторій при цьому все одно потрібен: конфіги (`caddy/`, `powersync/`,
`init/`, `db/`) сервіси монтують із нього, а `migrate` монтує з нього ж
`packages/db`. Накладка економить збірку застосунку, не клонування.

### Теги

| Тег | Звідки береться |
|-----|-----------------|
| `latest` | пуш у гілку за замовчуванням (`main`) і git-тег `vX.Y.Z` |
| `staging` | пуш у `staging` — поки V2 живе саме там, це найсвіжіший образ |
| `sha-<короткий-sha>` | кожен пуш — щоб відкотитись на конкретний коміт |
| `X.Y.Z` | git-тег `vX.Y.Z` |

### Що всередині образу

Рантайм — це `caddy:2-alpine` і статична збірка `apps/web` у `/srv`. Ні Node, ні
менеджерів пакетів у ньому немає. Раніше образ застосунку був Node-сервером
(Nitro), і MER-60 вирізав із нього npm, corepack і yarn руками — ~185 пакетів,
яких ніхто не виконував, з 16 CVE (1 Critical + 7 High + 8 Medium на
2026-08-10). Відколи окремий сервер застосунку прибрано, вирізати нема чого.

Щоб CVE не повернулися тихо з наступним оновленням бази, `docker-publish.yml`
після збірки сканує образ (`docker/scout-action`) і падає на будь-якій
Critical чи High. Те саме раз на тиждень робить скан за розкладом (нижче).

**Caddy в цьому образі зібраний нами, а не взятий з офіційного.** Саме на цьому
скан спіймав перший регрес: в образі `caddy:2-alpine` (збірка від 24.06.2026)
лежать 1 Critical + 13 High, і всі до одної — у Go-модулях, вкомпільованих у
бінарник: `stdlib` 1.26.3 (CVE-2026-39821 і ще шість), `x/crypto` 0.52.0,
`grpc` 1.81.0, `x/net` 0.55.0. Два очевидні шляхи не працюють: `apk upgrade` до
них не дотягується (це не пакети Alpine), а новішого тега немає — 2.11.4 і є
останній реліз Caddy, з червня. Тому шар `caddy-build` в `infra/web.Dockerfile`
компілює той самий Caddy 2.11.4 свіжим Go (1.26.8 проти потрібних 1.26.6) і з
піднятими модулями, а рантаймний шар підміняє рівно `/usr/bin/caddy`. Решта —
XDG-каталоги, `/data` із сертифікатами, команда за замовчуванням — лишається
від офіційного образу.

> Це тимчасовий шар. Щойно upstream випустить образ зі свіжими модулями, він і
> `infra/caddy-build/main.go` прибираються одним комітом. Перевірити:
> `docker run --rm --entrypoint caddy caddy:2-alpine build-info`.

Третій канал тих самих скарг — пакети самої Alpine. Тег базового образу довго
стоїть на одному знімку Alpine, тож виправлення до її пакетів виходять раніше,
ніж базу перезбирають: із 29.08.2026 `openssl 3.5.7-r0` давав 1 Critical + 7
High, а `3.5.8-r0` уже лежав у тій самій гілці `v3.24/main` (MER-67). Тому
образ оновлює пакети бази (`apk upgrade --no-cache`) — гілка Alpine лишається
прибитою тегом бази, тобто це патч-рівень, а не стрибок версії, і наступну CVE
базового образу цей рядок закриє сам.

Закриє, лише якщо справді виконається. Збірка в CI бере шари з кешу GHA, а
ключ кешу для `RUN apk upgrade --no-cache` — сама інструкція й шар бази, не
вміст репозиторію Alpine. Поки тег бази не зрушив, шар береться з кешу з
тими пакетами, які були на день першої збірки: 07.10.2026 скан упав на
`zlib 1.3.2-r0` (High), хоча `1.3.2-r1` уже лежав у `v3.23/main` (MER-106).
Тому рантаймна стадія називається `runtime`, і `docker-publish.yml` збирає її
без кешу (`no-cache-filters: runtime`). Це секунди: стадія лише оновлює пакети
й копіює готові артефакти. Стадії `build` і `caddy-build` кешуються, як і
раніше.

### Скан за розкладом

`docker-publish.yml` сканує образ лише в момент публікації, а CVE приходять і
без змін у коді: zlib із MER-106 з'явилась в уже опублікованому образі. Тому
`.github/workflows/image-scan.yml` раз на тиждень (понеділок, 06:00 UTC) і
вручну (Actions → Image Scan → Run workflow) сканує опубліковані теги
`staging` і `latest` тим самим `docker/scout-action` з тими самими порогами:
Critical чи High — червоний запуск (MER-108). Пороги записані в обох файлах
окремо, тож міняються теж в обох.

**Червоний скан — сигнал перезібрати образ, а не лагодити код.** Мердж у гілку
перепублікує її тег зі свіжими пакетами Alpine (рантаймна стадія без кешу,
див. вище): `staging` — мерджем у `staging`, `latest` — мерджем у `main` або
git-тегом `vX.Y.Z`. Лишився червоним і після перезбирання — значить,
виправлення ще не вийшло в гілці Alpine або CVE сидить у Go-модулях Caddy
(`caddy-build`), і це вже окрема задача.

- **Сканується тег, а не дайджест** — тобто рівно те, що зараз отримає
  `docker compose pull`. Тега немає в реєстрі — теж червоний запуск.
- **Розклад і кнопку Run workflow GitHub бере лише з гілки за замовчуванням**,
  тобто з `main`. Поки там V1 без цього файлу, workflow не запускається;
  запрацює сам після злиття `staging` → `main`. Те саме злиття вперше
  публікує `latest`, тож окремо «тега ще немає» тут не обробляється.
- **У публічному репозиторії GitHub вимикає розклад після 60 днів без
  комітів.** Тоді його вмикають знову кнопкою Enable workflow на сторінці
  workflow в Actions.

### Секрети репозиторію

Workflow нічого не публікує, доки в налаштуваннях репозиторію
(Settings → Secrets and variables → Actions) не з'являться два секрети:

| Секрет | Значення |
|--------|----------|
| `DOCKERHUB_USERNAME` | ім'я користувача Docker Hub — воно ж namespace, у який публікується образ |
| `DOCKERHUB_TOKEN` | **access token** Docker Hub із правом `Read & Write`, не пароль акаунта |

Токен, а не пароль: його видно в списку, можна відкликати окремо й він не
відмикає сам акаунт. Без секретів крок логіну падає — образ не публікується,
але код у репозиторії від цього не страждає.

## Розробка застосунку

Стек — це прод-збірка. Для роботи над інтерфейсом зручніше `pnpm dev` поруч із
уже піднятим стеком: він бере ту саму базу, той самий GoTrue і той самий sync,
але з гарячою заміною модулів.

```bash
docker compose up -d
docker compose exec -T caddy sh -c '. /secrets/app.env; printf "PUBLIC_SUPABASE_URL=%s\nPUBLIC_SUPABASE_ANON_KEY=%s\nPUBLIC_POWERSYNC_URL=%s/sync\n" "$PUBLIC_SUPABASE_URL" "$ANON_KEY" "$PUBLIC_SUPABASE_URL"' > apps/web/.env
pnpm install && pnpm dev
```

Другий рядок потрібен тому, що `pnpm dev` — це Vite поза стеком: змінні він
підставляє на етапі збірки, а anon-ключ існує лише всередині стека.

Міграції під час розробки — тим самим одноразовим сервісом, не з хоста:

```bash
docker compose up migrate
```

Порт Postgres назовні не публікується свідомо: до бази ходять лише сервіси
стека. Для разових запитів є `docker compose exec db psql -U postgres`.

## Рішення, які тут прийняті

**Секрети генеруються, а не запитуються.** Головна вимога до self-host —
`docker compose up` і нічого більше. Compose підставляє змінні, коли ЧИТАЄ
файл, тобто до старту будь-якого контейнера, — а отже згенерувати секрет і
одразу підставити його в той самий запуск неможливо. Тому сервіси, яким
потрібен секрет, стартують через тонку оболонку: вона читає `/secrets/app.env`
і через `exec` віддає керування рідній команді образу. `exec` обов'язковий —
інакше PID 1 лишається за `sh` і сигнал зупинки не доходить до сервісу.

> **Наслідок.** У образі PostgREST немає навіть `/bin/sh`, тож для нього
> оболонка неможлива — він єдиний отримує згенерований конфіг-файл і читає його
> сам. Файли в томі мають права 0644, а не 0600: GoTrue, PostgREST і PowerSync
> працюють не від root (uid `supabase`, 1000 і 901), і 0600 від root вони б не
> прочитали.

**Постачальник даних — не весь Supabase, а три його сервіси.** Офіційний
self-host — це ~11 контейнерів; застосунок звертається до трьох (GoTrue,
PostgREST, Postgres). Решта — Studio, Realtime, Storage, edge-функції,
аналітика з vector, пулер supavisor — у коді не згадується жодного разу.
Разом з ними пішли й дві найдорожчі пастки старої установки: орендар supavisor
у рядках підключення й накладка, яку Compose мовчки ігнорує, якщо не дописати
її в `COMPOSE_FILE`.

> Схема це витримує, бо вона ніколи й не залежала від Supabase: RLS читає GUC
> `request.jwt.claims` напряму, а не через `auth.jwt()`, і гранти
> `supabase_auth_admin` стоять під `IF EXISTS` (MER-44/45). Ролі `anon`,
> `authenticated`, `service_role`, `authenticator`, `supabase_auth_admin`
> приходять з образу `supabase/postgres` — `db/roles.sql` лише видає паролі
> двом, які реально входять у базу по мережі.

**Хук доступу — рядок у `compose.yaml`, а не окремий крок установки.** Без
`GOTRUE_HOOK_CUSTOM_ACCESS_TOKEN_*` GoTrue не покличе
`public.custom_access_token_hook`, у токені не буде claim `family_id`, і
застосунок не побачить жодного рядка — мовчки, без помилки (MER-45). Раніше це
був крок, який найлегше було пропустити; тепер його неможливо не зробити.

**Схему накочує стек, а не людина.** `migrate` — одноразовий сервіс, і все, що
працює з даними, чекає на його успішне завершення (`service_completed_successfully`).
Тому застосунок не може стартувати на базі без таблиць, RLS і хука. Власного
образу він не має: міграції накочує `psql` із того самого образу Postgres, що й
`db` (MER-69) — як саме, у `packages/db/README.md`.

**Сховище бакетів — Postgres, не MongoDB.** Демо PowerSync використовує MongoDB,
але це +2 сервіси (сам Mongo і ініціалізація реплікасету) й окремий рушій БД.
Postgres як bucket storage підтримується офіційно з 1.3.8; PowerSync створює
власну схему в указаній базі сам.

> **Наслідок для схеми (зроблено в MER-44).** Сховище живе в тій самій базі,
> яку PowerSync реплікує, тому публікація `powersync` перелічує таблиці явно —
> `CREATE PUBLICATION powersync FOR TABLE ...` у міграції
> `packages/db/migrations/0002_replication.sql`. Варіант `FOR ALL TABLES` затягнув
> би в реплікацію власні таблиці PowerSync і зациклив сервіс. Нову таблицю
> треба додавати в публікацію руками — інакше вона не поїде на пристрої.
> Так і зроблено в MER-55: `0003_prefs_shopping.sql` доповнює публікацію
> через `ALTER PUBLICATION powersync ADD TABLE`.

**Реплікація йде прямо в `db`.** Логічна реплікація потребує прямого з'єднання,
пулер її ламає — колись це означало «не через supavisor», тепер пулера в стеку
немає взагалі, і `PS_DATABASE_URI` дивиться на `db:5432`.

**Користувач реплікації — поки що `postgres`.** Так робить офіційне демо
PowerSync. Виділену роль `powersync_role` (`LOGIN REPLICATION BYPASSRLS` +
`SELECT` на таблицях схеми) уже заводить міграція MER-44, але **без пароля** —
секрети в git не потрапляють, а без пароля роль не може ввійти.

**PowerSync перевіряє токени спільним секретом, а не JWKS** (MER-46). GoTrue у
self-host досі підписує токени симетричним ключем: у них немає `kid`, а
`/.well-known/jwks.json` віддає `{"keys":[]}`. Тому в `service.yaml` поруч із
`jwks_uri` стоїть `supabase_jwt_secret`. Без нього sync відповідає
`401 PSYNC_S2101` («no key matched the token KID»), і виглядає це як «правила
не працюють», хоч і правила, і claim правильні. Обидва способи лишаються поруч
навмисно: після переходу на асиметричні ключі JWKS наповниться й почне вигравати
сам.

**Сервера застосунку немає — лише файли й конфіг.** Вхід робить браузер, сесія
живе на пристрої, тож від стека застосунку потрібен рівно публічний конфіг
(`PUBLIC_*`). Його Caddy вписує в `index.html` шаблоном (`templates`) на кожній
відповіді. Окремий Node-сервер існував саме заради цього, тепер у стеку на
контейнер менше. З `app.env` Caddy бере лише anon-ключ і читає файл у
підоболонці: шаблон уміє вивести в сторінку будь-яку змінну оточення, тож
`JWT_SECRET` і пароль бази в оточення Caddy не потрапляють узагалі.

## Перевірка на живому стеку

Що саме має бути видно, коли все справді працює:

```bash
# у токені є family_id — інакше RLS не покаже жодного рядка (MER-45)
docker compose logs auth | grep -i error

# бакет сім'ї зійшовся — claim доїхав і правила його прочитали (MER-46)
docker compose logs powersync | grep "New checkpoint"
```

У логах PowerSync після входу має з'явитися бакет
`family_data|0["<family_id>"]`. Порожньо й без помилок — див. абзац про хук
доступу вище.

## Розбіжності з інструкцією V2

Інструкція вимагає звіряти кожне ім'я з офіційною документацією і фіксувати
розбіжності. Знайдено чотири:

| В інструкції | Насправді | Джерело |
|--------------|-----------|---------|
| конфіг називається `powersync.yaml` | `service.yaml` (+ окремий `sync-config.yaml`), шлях задається `POWERSYNC_CONFIG_PATH` | `powersync-ja/self-host-demo` |
| `client_auth.allow_local_jwks` вмикає локальні JWKS-адреси | такого ключа більше немає; є зворотний `block_local_jwks` (типово `false`) | JSON-схема `@powersync/service-schema` |
| «bucket по `family_id`» | бакети — це legacy `bucket_definitions`; актуальні Sync Streams з `config: edition: 3`, параметр читається `auth.parameter('family_id')` | docs.powersync.com/sync/streams |
| для перевірки токенів досить `PS_JWKS_URL` | self-host GoTrue лишається на HS256, JWKS порожній — потрібен ще `client_auth.supabase_jwt_secret` | розділ вище, перевірено на живому стеку |

Імена змінних середовища з контракту (`PS_DATABASE_URI`, `PS_JWKS_URL`,
`PUBLIC_*`) збережено як є: у конфізі PowerSync вони підставляються через
`!env`, а той приймає будь-яке ім'я з префіксом `PS_`.
